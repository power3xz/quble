# flush 구조 - push, pull, commit

진행 중 설계다. 이 문서를 기준으로 논의한다. 합의한 것과 합의할 것을 나눠 적고, 합의가 끝난 항목은 "합의한 것"으로
옮긴다.

## 지금 구조

핸들러 하나가 끝날 때 바뀐 leaf를 모아 한 번에 처리하는 것을 flush라고 한다. 지금 flush는 두 단계다.

1. **통지 전 단계** - 바뀐 leaf를 파생 구독한 식 인스턴스를 모두 센다(`expr-layer.ts`의 `flush`).
2. **통지 단계** - 값이 바뀐 leaf의 통지 구독을 호출한다. DOM 갱신, `@if` 본문 바꾸기(`vm.ts`의
   `subscribeIfCond`), 개수 `@for`의 행 늘리기와 줄이기가 여기서 일어난다.

식 인스턴스를 셀지는 구독 표가 정한다. 구독되어 있으면 그 값을 누가 필요로 하는지 묻지 않고 센다.

## 문제

셀 대상이 고르기(`@if` 조건, 개수 `@for`의 개수, 삼항 cond)의 결과가 정해지기 전에 구독 표로 정해진다.

```
@if (i < n) { p() { ${rows[i].x} } }
```

rows 길이와 n이 3이고 핸들러가 i를 2에서 3으로 바꾸는 flush에서, 통지 전 단계가 `i < n`과 `rows[i].x`를 함께
센다. `rows[i].x`는 조건이 false가 된 것을 모른 채 `rows[3]`을 읽다가 RangeError를 throw한다. 본문은 그 뒤 통지
단계에서 떼어진다. 개수 `@for`의 떠나는 행, 삼항의 고르지 않은 갈래도 같은 문제다.

## 합의한 것

**flush를 push, pull, commit 세 단계로 나눈다.**

| 단계 | 하는 일 |
|---|---|
| push | 바뀐 leaf에서 그 leaf를 읽는 노드로 "다시 세야 함"을 알린다. 세지 않는다 |
| pull | 고르기가 먼저 고르고, 고른 쪽에 닿는 식 가운데 다시 세야 하는 것만 센다 |
| commit | DOM을 갱신하고, 고른 쪽이 바뀐 본문을 떼고 붙인다 |

위 예에서는 push가 두 식에 알리고, pull에서 `@if`가 `i < n`을 세어 false를 얻어 본문의 `rows[i].x`를 세지 않고,
commit에서 본문을 뗀다. 세 단계는 한 flush 안에서 이어서 돈다.

**식 안의 부분 재평가에 사용할 바뀐 변수는 push가 인스턴스의 `pendingVarMask`에 누적한다.** 변수 번호는 식 정의가
정하므로 같은 식의 인스턴스가 모두 같은 번호를 사용하고, 건너뛰기 표도 식 정의마다 하나다. 인스턴스마다 다른 것은
변수 번호에서 leafIndex로 가는 대응(`leafOfVar`)뿐이다.

`(a + 1) * (b + 2)`에서 a가 leaf 20, b가 leaf 21이면 `leafOfVar = [20, 21]`이다.

| 때 | 하는 일 |
|---|---|
| push | 바뀐 leaf 20의 구독을 따라 인스턴스에 닿으면 `leafOfVar`를 차례로 비교해 20인 자리(0번)의 비트를 켠다. `pendingVarMask \|= 0b01` |
| 평가 | `pendingVarMask`로 건너뛰기 표를 고르고(0b01이면 `b + 2`를 건너뜀), 평가한 뒤 0으로 지운다 |

OR로 켜기만 하므로 평가하기 전에 같은 leaf가 다시 바뀌어도 비트는 그대로고, 다른 변수가 바뀌면 그 비트가 더해진다.
지금은 `runPartial`이 평가할 때마다 바뀐 leaf 모음과 `leafOfVar`를 비교해 지역 변수로 같은 마스크를 만든다. 그
비교를 push로 옮기고 결과를 인스턴스에 남기는 것이다. 비교는 push 때의 `leafOfVar`로 하므로, 인덱스 접근이 읽는
leaf를 옮겨도 따로 고칠 것이 없다.

leafIndex에서 마스크로 가는 표를 인스턴스마다 두지 않고 비교하는 이유는 측정이다. 인스턴스 10000개, 한 번 찾는
시간이다.

| 식의 입력 수 | `leafOfVar` 비교 | 객체 | `Map` |
|---|---|---|---|
| 1 | 2.1ns | 20.9ns | 5.9ns |
| 2 | 5.7ns | 32.3ns | 6.4ns |
| 4 | 5.9ns | 38.8ns | 6.1ns |
| 8 | 7.9ns | 43.7ns | 6.8ns |

식의 입력은 대부분 1~4개라 비교가 가장 빠르거나 같고 메모리를 더 사용하지 않는다. `Map`과 객체는 인스턴스마다
약 190B 이상이 더 든다. 객체는 leafIndex처럼 흩어진 큰 숫자 키를 받으면 V8이 해시 표 방식으로 바꿔 가장 느리다.

**쉬는 본문과 쉬는 갈래의 구독은 유지한다.** 구독은 인스턴스를 만들 때 걸고 없앨 때(`release`) 푼다. 본문을 떼고
붙이는 것은 Region이 고른 쪽을 바꾸는 일일 뿐 구독을 건드리지 않는다.

```
@if (show) { ${a * b} }
```

| flush | 핸들러가 바꾼 것 | `a * b` 인스턴스 |
|---|---|---|
| 1 | show = false | 본문이 떼어져 쉰다. 구독은 그대로다 |
| 2 | a = 5 | push가 인스턴스에 "다시 세야 함"을 표시하고 `pendingVarMask`에 a의 비트를 켠다. pull은 고르지 않은 본문에 닿지 않아 세지 않는다 |
| 3 | a = 6 | 인스턴스에 이미 "다시 세야 함"이 표시되어 있어 push가 그 인스턴스를 품은 본문 쪽으로 다시 알리지 않는다. a의 비트도 이미 켜져 있다 |
| 4 | show = true | 본문이 다시 붙는다. 인스턴스에 "다시 세야 함"이 표시되어 있으므로 `pendingVarMask`로 부분 재평가하고, 표시를 지우고 마스크를 0으로 지운다 |

쉬는 동안 입력이 바뀌지 않은 인스턴스는 "다시 세야 함"이 표시되지 않아 다시 붙어도 세지 않는다. 쉬는 동안 바뀐 변수는
`pendingVarMask`에 누적되어 있으므로, 다시 붙은 본문도 계속 붙어 있던 본문과 같은 방식으로 평가한다.

지금 구현은 반대로 뗄 때 구독을 풀고(`detach`), 붙일 때 구독을 다시 걸면서 입력 leaf 전체를 바뀐 것으로 보고
다시 센다(`attach`). 구독이 풀린 동안에는 무엇이 바뀌었는지 기록되지 않기 때문이다. 유지하면 이 따라잡기가 필요
없어 `attachedCount`, `everAttached`, `catchUpLeaves`와 `attach`, `detach`의 구독 처리가 빠진다.

유지하는 쪽을 고른 근거는 측정이다. 같은 push, pull 모형 위에서 두 방식을 비교했고(식은 JS 함수로 흉내 내고 DOM
갱신은 넣지 않았다), 값은 flush 한 번의 평균이다.

| 장면 | 푸는 쪽 | 유지하는 쪽 | 구독 표 메모리(푸는 쪽 / 유지하는 쪽) |
|---|---|---|---|
| 탭 전환(탭 4개 x 1000행 x 3칸, 탭만 바꿈) | 229us | 2.1us | 715KB / 1031KB |
| 탭 + 시세 갱신(가격 400개를 바꾸고 10번에 한 번 탭 전환) | 54.9us | 48.3us | 715KB / 1028KB |
| 검색 타이핑(10000행 필터, 쉬는 행의 강조도 검색어를 읽음) | 1194us | 918us | 2393KB / 3175KB |
| 상품 목록 환율(10000행, 쉬는 할인 본문 9000개가 환율을 읽음) | 745us | 761us | 874KB / 3326KB |
| 시세표 + 숨긴 차트(5000종목을 매번 갱신) | 1245us | 1267us | 1213KB / 1213KB |
| 행 펼치기(10000행 중 한 행을 펼치거나 접음) | 0.7us | 0.3us | 650KB / 615KB |

- 푸는 쪽의 비용은 사용자가 본문을 바꾼 바로 그 flush에 몰린다. 본문 크기만큼 구독을 다시 걸고 인스턴스를 모두
  다시 센다. 실시간 반응성에서는 이 튀는 flush가 평균보다 중요하다.
- 유지하는 쪽의 비용은 메모리다. 쉬는 본문이 보이는 쪽과 같은 leaf를 읽으면 그 leaf의 구독 슬롯이 번호 하나에서
  Set으로 바뀐다. Set 하나가 약 200B라 상품 목록 환율 장면에서 약 2.4MB가 더 든다. 같은 구성의 1000행 인스턴스
  전체(실제 런타임, 테스트용 DOM 포함)가 약 15MB이므로 그 비율은 약 1.4%다.
- 푸는 쪽에는 flush가 끝나면 "다시 세야 함" 표시가 하나도 남지 않는다는 장점이 있다. 유지하면 쉬는 본문의
  인스턴스에 이 표시가 여러 flush 동안 남는다. 이 표시는 다시 붙을 때 평가할 인스턴스를 알려 주는 정보라 받아들인다.

## 합의할 것

세 단계를 어떻게 구현할지다. 항목마다 지금까지 나온 안을 적는다.

- **pull의 순서** - 시작점에서 하위로 그 자리에서 요청하는 방식(요청 순서), 다시 세야 하는 노드를 큐에 넣고 도는
  방식.
- **pull의 시작점** - 무엇을 처음 요청하는지, push가 그것을 어떻게 모으는지. 가지마다 요청 목록을 두는 안이 있다.
  이 안에는 식 인스턴스 -> 가지, 가지 -> Region, Region -> 가지 포인터가 필요하다(지금은 없다).
- **"다시 세야 함"을 어디에 어떻게 두는지** - 노드마다 비트, leaf마다 버전, 두 종류로 나눔
  (값이 그대로면 부모를 세지 않음).
- **식 인스턴스 사이의 간선(삼항부터)** - 하위 인스턴스의 결과 leaf를 `deriveSubscribers`로 구독, 하위 인스턴스
  번호를 둔 평평한 배열, 식 정의마다 CSR.
- **식 안의 부분 재평가** - skip table 유지, 다시 셀 연산 목록(레지스터 방식), 구간과 위치 비교.
- **작업 순서** - 바이트코드를 바꾸지 않는 `@if`와 개수 `@for`부터 할지, 삼항과 함께 할지.
