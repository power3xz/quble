# flush 구조 - push, pull, commit

진행 중 설계다. 이 문서를 기준으로 논의한다. 합의한 것과 합의할 것을 나눠 적고, 합의가 끝난 항목은 "합의한 것"으로
옮긴다.

## 지금 구조

핸들러 하나가 끝날 때 바뀐 leaf를 모아 한 번에 처리하는 것을 flush라고 한다. 지금 flush는 두 단계다.

1. **통지 전 단계** - 바뀐 leaf를 파생 구독한 식 인스턴스를 모두 센다(`expr-layer.ts`의 `flush`).
2. **통지 단계** - 값이 바뀐 leaf의 통지 구독을 호출한다. DOM 갱신, `@if` 본문 바꾸기(`vm.ts`의
   `subscribeIfCond`), 개수 `@for`의 행 늘리기와 줄이기가 여기서 일어난다.

식 인스턴스를 셀지는 구독 표가 정한다. 구독되어 있으면 그 값을 누가 필요로 하는지 묻지 않고 센다.

## 문제

셀 대상이 고르기(`@if` 조건, 개수 `@for`의 개수, 삼항 cond)의 결과가 정해지기 전에 구독 표로 정해진다.

```
@if (i < n) { p() { ${rows[i].x} } }
```

rows 길이와 n이 3이고 핸들러가 i를 2에서 3으로 바꾸는 flush에서, 통지 전 단계가 `i < n`과 `rows[i].x`를 함께
센다. `rows[i].x`는 조건이 false가 된 것을 모른 채 `rows[3]`을 읽다가 RangeError를 throw한다. 본문은 그 뒤 통지
단계에서 떼어진다. 개수 `@for`의 떠나는 행, 삼항의 고르지 않은 갈래도 같은 문제다.

## 합의한 것

**flush를 push, pull, commit 세 단계로 나눈다.**

| 단계 | 하는 일 |
|---|---|
| push | 바뀐 leaf에서 그 leaf를 읽는 노드로 "다시 세야 함"을 알린다. 세지 않는다 |
| pull | 고르기가 먼저 고르고, 고른 쪽에 닿는 식 가운데 다시 세야 하는 것만 센다 |
| commit | DOM을 갱신하고, 고른 쪽이 바뀐 본문을 떼고 붙인다 |

위 예에서는 push가 두 식에 알리고, pull에서 `@if`가 `i < n`을 세어 false를 얻어 본문의 `rows[i].x`를 세지 않고,
commit에서 본문을 뗀다. 세 단계는 한 flush 안에서 이어서 돈다.

**식 안의 부분 재평가에 사용할 바뀐 변수는 push가 인스턴스의 `pendingVarMask`에 누적한다.** 변수 번호는 식 정의가
정하므로 같은 식의 인스턴스가 모두 같은 번호를 사용하고, 건너뛰기 표도 식 정의마다 하나다. 인스턴스마다 다른 것은
변수 번호에서 leafIndex로 가는 대응(`leafOfVar`)뿐이다.

`(a + 1) * (b + 2)`에서 a가 leaf 20, b가 leaf 21이면 `leafOfVar = [20, 21]`이다.

| 때 | 하는 일 |
|---|---|
| push | 바뀐 leaf 20의 구독을 따라 인스턴스에 닿으면 `leafOfVar`를 차례로 비교해 20인 자리(0번)의 비트를 켠다. `pendingVarMask \|= 0b01` |
| 평가 | `pendingVarMask`로 건너뛰기 표를 고르고(0b01이면 `b + 2`를 건너뜀), 평가한 뒤 0으로 지운다 |

OR로 켜기만 하므로 평가하기 전에 같은 leaf가 다시 바뀌어도 비트는 그대로고, 다른 변수가 바뀌면 그 비트가 더해진다.
지금은 `runPartial`이 평가할 때마다 바뀐 leaf 모음과 `leafOfVar`를 비교해 지역 변수로 같은 마스크를 만든다. 그
비교를 push로 옮기고 결과를 인스턴스에 남기는 것이다. 비교는 push 때의 `leafOfVar`로 하므로, 인덱스 접근이 읽는
leaf를 옮겨도 따로 고칠 것이 없다.

leafIndex에서 마스크로 가는 표를 인스턴스마다 두지 않고 비교하는 이유는 측정이다. 인스턴스 10000개, 한 번 찾는
시간이다.

| 식의 입력 수 | `leafOfVar` 비교 | 객체 | `Map` |
|---|---|---|---|
| 1 | 2.1ns | 20.9ns | 5.9ns |
| 2 | 5.7ns | 32.3ns | 6.4ns |
| 4 | 5.9ns | 38.8ns | 6.1ns |
| 8 | 7.9ns | 43.7ns | 6.8ns |

식의 입력은 대부분 1~4개라 비교가 가장 빠르거나 같고 메모리를 더 사용하지 않는다. `Map`과 객체는 인스턴스마다
약 190B 이상이 더 든다. 객체는 leafIndex처럼 흩어진 큰 숫자 키를 받으면 V8이 해시 표 방식으로 바꿔 가장 느리다.

**쉬는 본문과 쉬는 갈래의 구독은 유지한다.** 구독은 인스턴스를 만들 때 걸고 없앨 때(`release`) 푼다. 본문을 떼고
붙이는 것은 Region이 고른 쪽을 바꾸는 일일 뿐 구독을 건드리지 않는다.

```
@if (show) { ${a * b} }
```

| flush | 핸들러가 바꾼 것 | `a * b` 인스턴스 |
|---|---|---|
| 1 | show = false | 본문이 떼어져 쉰다. 구독은 그대로다 |
| 2 | a = 5 | push가 인스턴스에 "다시 세야 함"을 표시하고 `pendingVarMask`에 a의 비트를 켠다. pull은 고르지 않은 본문에 닿지 않아 세지 않는다 |
| 3 | a = 6 | 인스턴스에 이미 "다시 세야 함"이 표시되어 있어 push가 그 인스턴스를 품은 본문 쪽으로 다시 알리지 않는다. a의 비트도 이미 켜져 있다 |
| 4 | show = true | 본문이 다시 붙는다. 인스턴스에 "다시 세야 함"이 표시되어 있으므로 `pendingVarMask`로 부분 재평가하고, 표시를 지우고 마스크를 0으로 지운다 |

쉬는 동안 입력이 바뀌지 않은 인스턴스는 "다시 세야 함"이 표시되지 않아 다시 붙어도 세지 않는다. 쉬는 동안 바뀐 변수는
`pendingVarMask`에 누적되어 있으므로, 다시 붙은 본문도 계속 붙어 있던 본문과 같은 방식으로 평가한다.

구독은 vm이 인스턴스를 만들 때 걸고(`subscribeInputs`) `release`가 heldByBranchCount 0에서 푼다. 다시 붙는 본문은 region이
식 인스턴스마다 `recountPending`을 호출한다. pull과 같은 요청이라 incoming edge의 시작점을 먼저 요청하고, 마스크가
남은 인스턴스만 센다. 4의 평가가 이것이다. 가지의 통지 구독(`TBranch.updateFns`)은 지금처럼 뗄 때 풀고 붙일 때
다시 걸며 현재 값으로 DOM을 맞춘다(`TBranch.everAttached`).

이전 구현은 뗄 때 파생 구독을 풀고(`detach`), 붙일 때 다시 걸면서 입력 leaf 전체를 바뀐 것으로 보고 다시
셌다(`attach`). 구독이 풀린 동안에는 무엇이 바뀌었는지 기록되지 않기 때문이다. 유지하면서 `attachedCount`,
`TExprInstance.everAttached`와 `attach`, `detach`가 빠졌다. 3의 "다시 알리지 않는다"는 push가 마스크가 0이던
인스턴스만 다시 셀 목록에 넣는 것이다 - 앞선 flush에서 평가하지 않아 마스크가 남은 인스턴스는 다시 붙을 때 센다.

유지하는 쪽을 고른 근거는 측정이다. 같은 push, pull 모형 위에서 두 방식을 비교했고(식은 JS 함수로 흉내 내고 DOM
갱신은 넣지 않았다), 값은 flush 한 번의 평균이다.

| 장면 | 푸는 쪽 | 유지하는 쪽 | 구독 표 메모리(푸는 쪽 / 유지하는 쪽) |
|---|---|---|---|
| 탭 전환(탭 4개 x 1000행 x 3칸, 탭만 바꿈) | 229us | 2.1us | 715KB / 1031KB |
| 탭 + 시세 갱신(가격 400개를 바꾸고 10번에 한 번 탭 전환) | 54.9us | 48.3us | 715KB / 1028KB |
| 검색 타이핑(10000행 필터, 쉬는 행의 강조도 검색어를 읽음) | 1194us | 918us | 2393KB / 3175KB |
| 상품 목록 환율(10000행, 쉬는 할인 본문 9000개가 환율을 읽음) | 745us | 761us | 874KB / 3326KB |
| 시세표 + 숨긴 차트(5000종목을 매번 갱신) | 1245us | 1267us | 1213KB / 1213KB |
| 행 펼치기(10000행 중 한 행을 펼치거나 접음) | 0.7us | 0.3us | 650KB / 615KB |

- 푸는 쪽의 비용은 사용자가 본문을 바꾼 바로 그 flush에 몰린다. 본문 크기만큼 구독을 다시 걸고 인스턴스를 모두
  다시 센다. 실시간 반응성에서는 이 튀는 flush가 평균보다 중요하다.
- 유지하는 쪽의 비용은 메모리다. 쉬는 본문이 보이는 쪽과 같은 leaf를 읽으면 그 leaf의 구독 슬롯이 번호 하나에서
  Set으로 바뀐다. Set 하나가 약 200B라 상품 목록 환율 장면에서 약 2.4MB가 더 든다. 같은 구성의 1000행 인스턴스
  전체(실제 런타임, 테스트용 DOM 포함)가 약 15MB이므로 그 비율은 약 1.4%다.
- 푸는 쪽에는 flush가 끝나면 "다시 세야 함" 표시가 하나도 남지 않는다는 장점이 있다. 유지하면 쉬는 본문의
  인스턴스에 이 표시가 여러 flush 동안 남는다. 이 표시는 다시 붙을 때 평가할 인스턴스를 알려 주는 정보라 받아들인다.

**push와 pull은 의존 그래프 하나로 처리한다.** 소유 트리(식 인스턴스 -> 가지 -> Region)는 flush에 쓰지 않는다.

- 노드는 식 인스턴스다. 간선 `A --> B`는 "B를 평가하기 전에 A를 먼저 확정해야 한다"는 뜻이다. 노드를 기준으로
  들어오는 간선을 incoming edge, 나가는 간선을 outgoing edge라고 부른다. outgoing edge가 없는 노드를 sink라고 부른다.
- leaf는 노드가 아니다. 바뀐 입력 leaf에서 그 leaf를 읽는 식 인스턴스를 찾는 곳(`deriveSubscribers`)과 평가한 값을
  기록하는 곳(`resultLeaf`)에만 leaf가 나온다.
- 간선은 간선 표에 한 번만 저장한다. 간선마다 시작점, 끝점, label을 두고, 노드에는 incoming edge와 outgoing edge의
  간선 번호만 기록한다. label이 한 곳에만 있어 양쪽 기록이 어긋나지 않고, 간선을 지울 때 간선 표의 한 줄만 지운다.
- 공유된 식 인스턴스는 복제하지 않는다. 그래서 그래프는 트리가 아니라 DAG(방향 비순환 그래프)다. sink마다 복제해
  트리로 만들면, 행 1000개의 삼항이 같은 조건을 읽을 때 조건을 1000번 평가하게 된다.

**고르기는 labeled edge로 나타낸다.** label은 then, else, 행 k 셋이다. 고르기를 위한 노드를 따로 두지 않는다.

| 고르기 | labeled edge |
|---|---|
| `@if (c)` | 조건 식 인스턴스 -> then 가지의 식 인스턴스(label then), else 가지의 식 인스턴스(label else) |
| 삼항 `c ? a : b` | 조건 식 인스턴스 -> 갈래 a(label then), 갈래 b(label else) |
| 개수 `@for (k of n)` | 개수 식 인스턴스 -> 행 k의 식 인스턴스(label 행 k) |

```
${a ? b : c}

[a] --(then)--> [b]
[a] --(else)--> [c]
[a] ----------> [삼항]
[b] ----------> [삼항]
[c] ----------> [삼항]
```

- 조건이 입력 leaf 하나(`@if (show)`, `@for (k of n)`)여도, 본문을 그리면 식 인스턴스가 생기면 컴파일러가 그
  leaf 하나를 읽는 식으로 조건을 낸다(`IF_EXPR`, `FOR_COUNT_EXPR`). labeled edge의 시작점이 될 노드가 있어야 하기
  때문이다. 이런 `@if`와 `@for`마다 식 인스턴스 하나와 결과 leaf 하나가 늘어난다. 본문에 식 인스턴스가 없으면
  간선을 걸 대상이 없어 지금처럼 `IF`, `FOR_COUNT_VAR`로 낸다. 본문에 자식 컴포넌트가 있으면 지금은 자식 템플릿을
  보지 않고 식 인스턴스가 생긴다고 본다. 자식 템플릿까지 따라가 판정하는 것은 나중에 한다.
- 배열 `@for`는 label을 새로 만들지 않는다. 행 가지는 부모 가지의 간선(시작점과 label)을 물려받는다 - 부모가
  `@if` 가지면 그 조건이 false일 때 행의 식 인스턴스도 평가하지 않는다. 지운 행은 handler(`removeAt`)에서 바로
  해제되어 flush 때는 이미 없다.
- 간선은 가지가 식 인스턴스를 실을 때 vm이 걸고(`addExprInstance`), 가지가 없어질 때 region이 지운다
  (`freeBranchTree`). 가지마다 간선의 시작점과 label을 둔다(`TBranch.edgeStartNode`, `edgeLabel`).

**push는 outgoing edge를 따라간다.**

1. 바뀐 leaf를 읽는 식 인스턴스 전부에 dirty 표시를 한다(`pendingVarMask`에 비트를 켠다).
2. label이 없는 outgoing edge를 따라가며 check 표시를 한다. 이미 표시가 있는 노드에서 멈춘다.
3. labeled edge로는 표시를 보내지 않는다. labeled edge의 끝점은 시작점의 값으로 계산되지 않아, 시작점이 바뀌어도
   끝점의 값은 그대로다.
4. label이 없는 간선을 따라가 닿은 끝 노드를 평가를 시작할 목록에 넣는다. dirty 표시를 한 노드에 따라갈 간선이
   처음부터 없으면 그 노드 자신이 끝이다. `@if (show)`의 `[show]`는 labeled edge만 있어 자신이 끝이고, 삼항의
   조건 `[a]`는 `[a] --> [삼항]`을 따라가 `[삼항]`이 끝이다.

**pull은 요청 방식이다.** 평가를 시작할 목록의 노드를 요청한다. 요청받은 노드는 incoming edge의 시작점을 먼저
요청한다. incoming labeled edge가 있으면, 그중 하나라도 시작점의 값이 label과 맞을 때만 평가한다(공유된 식
인스턴스는 incoming labeled edge가 여럿일 수 있다). label이 맞지 않아 평가하지 않은 노드는 `pendingVarMask`를
그대로 둔다.

조건 없는 가지도 그 식 인스턴스를 가지면 간선과 관계없이 평가한다. `${x}`가 root와 `@if (c)` 안에 함께 있으면
c가 false여도 root의 x는 갱신되어야 한다. 식 인스턴스를 가진 가지 수가 `heldByBranchCount`이고, 그중 조건 아래 가지 수가
incoming labeled edge 수다. incoming labeled edge 수가 `heldByBranchCount`보다 작으면 조건 없는 가지가 있다는 뜻이라
간선을 보지 않고 평가한다.

| label | 맞는 경우 |
|---|---|
| then | 시작점의 값이 truthy |
| else | 시작점의 값이 falsy |
| 행 k | k < 시작점의 값 |

`a`가 true일 때 c가 읽는 leaf가 바뀌면:

```
push  [c] dirty -> [삼항] check -> 평가를 시작할 목록: [삼항]
pull  [삼항]을 요청한다
        [a] 표시가 없다 (true)
        [b] 표시가 없다
        [c] label else와 맞지 않는다 -> 평가하지 않는다. pendingVarMask는 남는다
      [삼항]은 check만 있고 요청한 노드 중 값이 바뀐 것이 없다 -> 평가하지 않는다
```

`@if (show) { ${a} }`에서 show만 바뀌면 `[a]`는 요청받지 않는다. a는 바뀌지 않았으므로 평가할 것이 없고, 가지 교체는
commit이 한다.

in-degree로 순서를 정하는 Kahn 방식은 쓰지 않는다. incoming edge가 없는 노드부터 처리하므로 삼항의 고르지 않은
갈래를 조건보다 먼저 평가하고, flush마다 표시된 노드 사이의 in-degree를 세고 지워야 한다. 재귀 요청의 깊이는 식이
중첩된 정도라 스택을 넘지 않는다.

**DOM을 바꾸는 일은 모두 commit이 한다.** 가지를 붙이고 떼는 일, 처음 붙는 가지를 만드는 일, 행을 늘리고 줄이는
일이다. pull이 끝난 뒤라 기존 식 인스턴스의 결과 leaf가 최신이다. 새로 붙는 가지에서는 `pendingVarMask`가 0이 아닌
식 인스턴스만 평가한다.

## 합의할 것

세 단계를 어떻게 구현할지다. 항목마다 지금까지 나온 안을 적는다.

- **check 표시를 어디에 어떻게 두는지** - dirty는 `pendingVarMask`가 0이 아닌 것으로 나타낸다. check는 노드마다
  비트, leaf마다 버전 중에서 정한다.
- **식 안의 부분 재평가** - skip table 유지, 다시 셀 연산 목록(레지스터 방식), 구간과 위치 비교.
- **작업 순서** - `@if`와 개수 `@for`의 labeled edge는 끝났다(`FOR_COUNT_EXPR`를 더해 바이트코드가 바뀌었다).
  쉬는 본문의 구독 유지도 끝났다. 남은 것은 삼항이다.
