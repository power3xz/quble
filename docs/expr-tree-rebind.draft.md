# 식을 트리로 보면 - 구독 재배선

값 자리 식에 배열 인덱스 접근(`${a[i].b}`)이 들어오면서 생긴 문제와, 식을 트리로 놓고
봤을 때 나온 해법을 적는다. 지금 바이트코드는 후위 표기라 트리가 없는데, 트리에서 얻은
판정을 후위 표기에서 어떻게 되살리는지가 3절이다.

진행 중 설계다 - 확정되면 DESIGN.md/BYTECODE.md로 옮기고 이 문서는 지운다.

## 1. 문제

식이 읽는 leafIndex가 실행 중에 달라진다.

```
${a[i].b}   i = 0 이면 a[0].b 칸을, 1이면 a[1].b 칸을 읽는다
```

구독은 처음 평가할 때 읽은 칸에 걸린다. `i`가 0에서 1로 바뀌면 식을 다시 평가해 화면은
맞게 고치지만, 구독은 `a[0].b`에 남는다. 그 뒤 `a[1].b`가 바뀌어도 아무도 깨어나지 않는다.

인덱스 접근이 없는 식은 이 문제가 없다 - `${count * 2}`가 읽는 칸은 처음 정해지면 끝까지
같다.

## 2. 트리로 보면

식은 본래 트리다. 후위 표기는 그 트리를 평평하게 편 것이다.

```
a[i].b + c[j].d

              Add
            /     \
      Field(b)    Field(d)
          |           |
       Index       Index
       /    \      /    \
      a      i    c      j
```

**`Index`의 두 간선은 성격이 다르다.** 배열 쪽은 어디를 뒤질지 정하고(값이 안 변한다 -
arrayInfoIndex), 인덱스 쪽은 그중 몇 번째인지 정한다. 인덱스 쪽 값이 바뀌면 그 `Index`가
읽을 leafIndex가 달라진다.

그래서 각 노드가 읽을 leafIndex가 달라지는 조건이 이렇게 나뉜다.

```
Var/Field   부모가 달라지면 나도 달라진다
Index       인덱스 쪽 자식의 값이 달라지면 달라진다
연산자      읽는 leafIndex가 없다 - 값만 낸다
```

**영향은 바뀐 칸에서 루트로 올라가는 경로에만 미친다.** 형제 가지는 그대로다.

| 바뀐 칸 | 값이 달라지는 노드 | 읽을 leafIndex가 달라지는 노드 |
|---|---|---|
| `i` | Index(a,i), Field(b), Add | Index(a,i), Field(b) |
| `j` | Index(c,j), Field(d), Add | Index(c,j), Field(d) |
| `a[i].b` 칸 | Field(b), Add | 없음 |

`Add`는 값만 달라진다 - 연산자라 읽는 자리가 없다.

중첩되면 연쇄가 인덱스 간선을 타고 올라간다.

```
a[b[k]].q

        Field(q)
           |
         Index
        /      \
       a      Index
              /    \
             b      k
```

`k`가 바뀌면 `Index(b,k)`가 읽을 자리가 달라지고, 그 값이 곧 `a`의 인덱스라 `Index(a,·)`도
달라진다. 재구독 대상이 둘이다 - `b[k]` 요소 칸과 `a[b[k]].q` 요소 칸.

## 3. 후위 표기와의 연결

트리를 유지하지 않아도 된다. **부분식은 후위 표기에서 연속 구간**이기 때문이다.

```
a[i].b + c[j].d

[LoadVar a][LoadVar i][ElemAt][FieldAt][ReadLeaf][LoadVar c][LoadVar j][ElemAt][FieldAt][ReadLeaf][Add]
└──────────── a[i].b ────────────────────────┘└──────────── c[j].d ───────────────────────────┘
                       └ i │
                      인덱스 가지
```

구간 경계는 컴파일러가 트리를 펼 때 안다. 런타임도 식을 처음 만들 때 후위 바이트를 스택으로
한 번 훑으면 같은 경계를 얻는다 - 부분 재평가(expr-partial-reeval.draft.md)가 이 방법으로
부분식 구간을 얻었다.

**재배선에 필요한 구간은 인덱스 가지 하나다.** 그 구간을 얻는 방법이 둘이다.

- 컴파일러가 싣는다 - `ElemAt`에 인덱스 가지 길이를 operand로 실으면 런타임이 "직전 n바이트가
  인덱스 가지였다"를 안다.
- 런타임이 식을 만들 때 한 번 훑어 얻는다 - 포맷이 그대로다.

어느 쪽이든 그 구간에서 읽은 칸을 재구독 대상으로 나눈다.

```
지금    ElemAt                 (0x1f)
바꾸면  ElemAt indexLen:u8     (0x1f, 길이 1바이트)

a[i].q -> 인덱스 가지가 LoadVar(i) 3바이트 -> ElemAt 3
```

중첩은 저절로 맞는다 - 안쪽 `ElemAt`의 구간이 바깥 구간에 통째로 들어간다.

```
a[b[k]].q

[LoadVar a][LoadVar b][LoadVar k][ElemAt][ReadLeaf][ElemAt][FieldAt][ReadLeaf]
           └───── 바깥 ElemAt의 인덱스 가지 ──────┘
                      └ 안쪽 ElemAt의 ┘
                         인덱스 가지
```

### 정할 것

- 구간을 컴파일러가 실을지 런타임이 얻을지.
  - operand 방식은 포맷 변경이라 BYTECODE.md, codegen, 런타임, qubb 인스펙터가 따라 바뀐다.
  - 런타임 방식은 같은 식의 인스턴스마다 훑지 않도록 식 정의 하나당 한 번 얻어 공유해야 한다.
- operand를 싣는다면 `u8`은 인덱스 식이 255바이트를 넘을 때 길이를 담지 못한다. 컴파일러가 그
  자리에서 에러를 내는 방식은 `offset`이 이미 쓰고 있다.

## 4. 재배선 규칙

3절의 구간 판정이 서면 규칙은 둘로 끝난다.

| 어디서 읽었나 | 그 칸이 바뀌면 |
|---|---|
| 인덱스 가지 안 | 재평가 + 재구독 |
| 그 밖 | 재평가만 |

`a[i].b + c[j].d`에서 `i`가 바뀌면 `a[i].b` 칸만 다시 걸고 `c[j].d`는 안 건드린다.

재구독은 인덱스 접근이 있는 식에서만, 그것도 인덱스가 바뀐 경우에만 일어난다. 인덱스
접근이 없는 식(`count * 2`)은 재배선 경로를 아예 안 탄다.

## 5. 같은 구조가 여는 것 - 부분 재평가

부분식이 연속 구간이라는 사실은 부분 재평가로도 이어진다 - 바뀐 칸과 무관한 부분식은
계산하지 않고 이전 값을 쓴다. 인덱스 접근과 무관하게 모든 식에 걸리는 얘기라
expr-partial-reeval.draft.md에 따로 적는다.
