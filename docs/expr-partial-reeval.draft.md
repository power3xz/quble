# 부분 재평가 - 바뀌지 않은 부분식 건너뛰기

지금은 식이 읽는 칸 하나가 바뀌면 식 전체를 처음부터 다시 평가한다. 바뀐 칸을 품지 않은
부분식은 계산하지 않고 지난번 값을 쓰면 된다. 배열 인덱스 접근이 없는 식을 대상으로 설계하고
쟀다 - 인덱스 접근과의 결합은 7절에 남은 것으로 둔다.

진행 중 설계다 - 확정되면 DESIGN.md/BYTECODE.md로 옮기고 이 문서는 지운다.

## 1. 동작

후위 바이트를 앞에서부터 도는 것은 그대로다. 부분식이 시작하는 자리에서 "이 부분식이 바뀐
칸을 품는가"만 보고, 안 품으면 지난번 값을 스택에 올린 뒤 부분식 끝 다음으로 건너뛴다.

```
(a + b) * (c - d)

순번   0  1  2    3  4  5    6
       a  b  Add  c  d  Sub  Mul
```

| c가 바뀌면 | 한 일 |
|---|---|
| 순번 0 | `Add`(0-2)는 c(순번 3)를 안 품는다 - `Add`의 지난번 값을 올리고 순번 3으로 |
| 순번 3~5 | `c`, `d`를 읽고 `Sub`를 계산 |
| 순번 6 | `Mul`을 계산 |

## 2. 필요한 것

| 무엇 | `((a + b) + c) + d`에서 |
|---|---|
| 연산 노드마다 지난번 값 | `Add` 셋의 값 |
| `outermostOpAt` - 순번마다 거기서 시작하는 가장 바깥 연산 노드 | 순번 0 -> 루트 `Add` |
| `innerOpAt` - 연산 노드마다 같은 순번에서 시작하는 한 겹 안쪽 연산 노드 | 루트 `Add` -> `(a + b) + c` -> `a + b` |
| `parentOp` - 노드마다 부모 연산 노드(4절의 판단에 쓴다) | 순번 0의 `a` -> `a + b` |
| leafIndex마다 식에 나오는 순번(오름차순) | `a` -> [0] |

- 부분식이 시작하는 잎은 부모의 왼쪽 자식인 잎이다(단항 연산의 자식도 왼쪽으로 친다).
  `outermostOpAt`은 그런 잎의 순번에만 값이 있다. 트리로 보면 잎에서 위로, 왼쪽 자식인
  동안 올라가 멈춘 노드가 가장 바깥 노드다.
- 잎은 값을 따로 들지 않는다 - store에 있다.
- 연산 노드의 부분식 끝은 그 노드 자기 순번이라 시작만 알면 된다.
- 지난번 값을 뺀 셋은 식 바이트만으로 정해진다. 식을 만들 때 후위 바이트를 스택으로 한 번
  훑어 얻고, 같은 식의 인스턴스끼리 공유할 수 있다.

## 3. 판정

부분식은 늘 잎에서 시작한다. 그래서 판정은 `outermostOpAt`에 값이 있는 잎 순번에서만 한다 -
연산 순번이나 오른쪽 자식인 잎(`c - d`의 `d`)은 거기서 시작하는 부분식이 없다.

```
가장 바깥 노드부터, 그 노드가 바뀐 위치를 품는 동안 한 겹 안쪽 노드(innerOpAt)로 들어간다
남은 노드가 있으면 그 지난번 값을 올리고 그 노드 순번 + 1로 건너뛴다
```

`((a + b) + c) + d`에서 `d`(순번 5)가 바뀌면

| 본 노드 | 끝 | 5를 품나 | 한 일 |
|---|---|---|---|
| 루트 `Add` | 6 | 품음 | 안쪽으로 들어감 |
| `(a + b) + c` | 4 | 안 품음 | 지난번 값을 올리고 순번 5로 |

**들어가는 횟수가 할 일의 양을 넘지 않는다.** 들어가며 지나치는 노드는 바뀐 위치를 품은 노드,
곧 어차피 다시 계산할 노드다. 그래서 판정 비용을 다 더해도 건너뛴 부분식 수와 다시 계산하는
노드 수의 합 이하다 - 판정 한 번당 분할 상환 O(1).

같은 leafIndex가 식에 여러 번 나오면 "pc 이후 가장 가까운 바뀐 위치" 하나만 들고 판정한다.
pc가 앞으로만 가서 이 위치도 앞으로만 옮겨 간다.

## 4. 캐시를 쓸지 판단

건너뛸 것이 없으면 판정 비용만 더해져 처음부터 평가하는 것보다 느리다(최악 2배). 그래서
leafIndex마다 캐시를 쓸지 식을 만들 때 정해 둔다.

```
다시 계산할 연산 수 / 식 전체의 연산 수 <= 0.75 이면 캐시, 넘으면 처음부터 평가
```

다시 계산할 연산은 그 잎이 나오는 순번에서 루트까지 올라가는 경로 위의 연산이다. 여러 번
나오면 경로를 합치고 겹치는 연산은 한 번만 센다. 식 바이트만으로 정해지므로 런타임에서는
표를 한 번 읽는 것으로 끝난다.

처음부터 평가할 때도 연산 노드의 지난번 값을 모두 새로 써 둔다 - 다음에 다른 잎이 바뀌어
캐시를 쓸 때 맞아야 한다.

0.75는 잰 값이다(5절의 측정 방법, ns/회).

| 다시 계산할 비율 | 식, 바뀐 잎 | 늘 캐시 | 처음부터 | 빠른 쪽 |
|---|---|---|---|---|
| 50.2% | 왼쪽 겹 합(잎 256), 가운데 잎 | 685 | 899 | 캐시 |
| 62.5% | 폼 검증 `&&` 사슬, 첫 항의 잎 | 38 | 45 | 캐시 |
| 66.7% | `(a + b) * (c - d)`, c | 23 | 22 | 비슷 |
| 75% | 문자열 `+` 균형, 넷째 항 | 76 | 95 | 캐시 |
| 80% | 금액 식, 첫 잎 | 31 | 28 | 처음부터 |
| 100% | 왼쪽 겹 합(잎 256), 첫 잎 | 1440 | 910 | 처음부터 |

## 5. 측정

Node에서 식 평가만 쟀다 - DOM 갱신은 빠져 있다. 식 19개(최악 7개, 실제 템플릿에 흔한 식 12개).
실제 식은 폼 검증 `&&` 사슬, 권한 조건, 문자열 `+` 이어 붙이기, 금액 산술이고 잎은 5~6개다.

| 식, 바뀐 잎 | 처음부터 | 판단(0.75) | alien-signals 식 전체 computed |
|---|---|---|---|
| 균형 트리(잎 256), 한 잎 | 1023 | 62 | 1206 |
| 왼쪽 겹 합(잎 256), 첫 잎 | 919 | 907 | 1045 |
| 폼 검증 `&&` 사슬, 마지막 잎 | 46 | 17 | 51 |
| 금액 식, 첫 잎 | 28 | 30 | 37 |
| 문자열 `+` 사슬, 둘째 항 | 92 | 95 | 90 |

- 판단 방식은 19개 중 18개에서 alien-signals의 식 전체 computed보다 빠르거나 같다. 느린 하나는
  문자열 `+` 사슬이고 차이가 흔들림 범위 안이다.
- 처음부터 평가하는 해석기만으로도 19개 중 15~17개(측정마다 다름)에서 alien-signals보다
  빠르다. 느린 쪽은 문자열 `+` 식이고 차이는 10% 안쪽이다.
- 실제 크기 식에서 아끼는 시간은 갱신 한 번에 수십 ns다.

**재는 방법이 결과를 바꿨다.**

- 여러 구현을 한 프로세스에서 차례로 재면 V8의 최적화 상태가 서로 섞여 같은 코드가 측정마다
  1.5배까지 흔들렸다. 이 흔들림 때문에 "비율 하나로는 나눌 수 없다", "해석기가 JS 함수보다
  느리다"는 틀린 결론을 한때 냈다. 식과 구현 조합마다 node 프로세스를 따로 띄워 잰다.
- 라운드 최솟값은 GC 비용을 가린다. 라운드 21개의 중앙값과 최소-최대를 같이 본다.

## 6. 버린 안

| 안 | 버린 이유 |
|---|---|
| 명령어에 건너뛸 자리를 표시 - 컴파일러가 부분식 앞에 `SKIP`(건너뛸 곳, 캐시 칸), 뒤에 `STORE`를 넣고 칸마다 잎 비트마스크를 싣는다 | 런타임 분석은 없어지지만 갱신 속도 이득이 없다. 건너뛸 것이 없을 때 처음부터 평가로 돌아가지 못해 최악 2배 느리다(1682 대 910). 표시할 최소 연산 수를 올려도 풀리지 않는다 |
| leafIndex마다 점프표(순번 -> 건너뛸 곳) | 판정이 O(1)이지만 메모리가 식에 나오는 잎 수만큼 는다. 2절 구조가 분할 상환 O(1)로 같은 일을 한다 |
| 결합/분배 법칙으로 식 모양 바꾸기 - 왼쪽 겹 사슬을 균형 트리로, `x*b0 + x*b1`을 `x*(b0 + b1)`로 | number가 부동소수점이라 묶는 순서를 바꾸면 값이 달라진다(`(0.1 + 0.2) + 0.3` 대 `0.1 + (0.2 + 0.3)`). 잎 5~6개 식에서는 앞쪽 잎은 빨라지고 뒤쪽 잎은 느려져 득실이 섞인다 |

## 7. 남은 것

- **실제 opcode로 넓히기**
  - 단항 연산(`Not`, `Neg`)은 자식이 하나다. 그 자식을 왼쪽 자식으로 쳐 `innerOpAt`에 잇는다.
  - `LoadVar` 슬롯(CONST 슬롯, `LoadArrayLength`, `LoadStringLength`)을 잎으로 다뤄야 한다.
- **인덱스 접근과 결합** - `a[i].b`가 읽는 칸은 바이트에 없고 실행 중에 정해진다. "leafIndex가
  식의 어느 순번에 나오는가"라는 2절의 전제가 깨진다. expr-tree-rebind.draft.md의 재배선과 함께
  설계한다.
- **분석표 공유** - 식 정의 하나당 한 번 만들어 인스턴스끼리 공유한다. 인스턴스마다 만들면
  `@for` 회차 수만큼 분석한다.
- **여러 칸이 한 번에 바뀌는 경우** - 핸들러 하나가 칸 여럿을 바꿀 때 한 칸씩 차례로 다시
  평가해도 맞는지 본다.
- **브라우저에서 DOM 갱신까지 포함해 재기** - 갱신 한 번에 아끼는 수십 ns가 DOM 쓰기 옆에서
  드러나는지 본다. 드러나지 않으면 넣지 않는다.
- **메모리와 식 생성 비용 재기**.
