# 부분 재평가 - 바뀌지 않은 부분식 건너뛰기

식이 읽는 칸 하나가 바뀌면, 그 칸을 품지 않은 부분식은 계산하지 않고 지난번 값을 쓴다. 값 자리
식(텍스트 보간, 속성값)과 `@if` 조건 식 모두 이렇게 다시 센다. 배열 인덱스 접근 식(`a[i].b`)도
포함한다.

구현은 core/web/expr-skip-table.ts(표)와 runtime.ts의 `subscribeExpr`, `runExpr`(평가)다. 표의
각 필드가 무엇을 담는지는 expr-skip-table.ts 주석에 예시와 함께 있다 - 여기서는 왜 이렇게
정했는지를 적는다.

진행 중 설계다 - 확정되면 DESIGN.md/BYTECODE.md로 옮기고 이 문서는 지운다.

## 1. 동작

후위 바이트를 앞에서부터 도는 것은 처음 셀 때와 같다. 잎 위치에 "여기서 시작하는 부분식을
건너뛰라"는 표시가 있으면, 그 부분식의 끝 연산까지 계산하지 않고 그 연산의 지난번 값을 스택에
올린 뒤 끝 연산 다음 명령으로 간다.

```
(a + b) * (c - d)

위치   0          3          6    7          10         13   14
       LOAD_VAR a LOAD_VAR b ADD  LOAD_VAR c LOAD_VAR d SUB  MUL
```

c가 바뀌면 건너뛸 표는 `{ 0: 6 }`이다.

| 위치 | 한 일 |
|---|---|
| 0 | 표에 0 -> 6이 있다. `a + b`(끝 ADD 6)의 지난번 값을 올리고 7로 간다 |
| 7~13 | `c`, `d`를 읽고 `SUB`를 계산 |
| 14 | `MUL`을 계산 |

- 부분식은 후위 바이트에서 이어진 구간이고, 늘 잎에서 시작한다. 시작하는 잎은 부모의 왼쪽
  자식인 잎이다(단항 연산의 자식도 왼쪽으로 친다). 그래서 표의 키는 잎 위치뿐이다.
- 끝 연산 다음 명령은 `끝 위치 + 그 명령의 바이트 수`다. `FIELD_AT`처럼 operand가 붙은 연산이
  끝일 수 있어 `+ 1`이 아니다.

## 2. 무엇을 미리 계산하고 무엇을 인스턴스마다 드는가

**식 정의당 한 번** - 식 바이트만으로 정해져, 같은 식을 쓰는 인스턴스(`@for` 회차마다 생기는 것)가
공유한다. 런타임이 식 바이트 객체를 키로 한 `WeakMap`에 둔다.

| 무엇 | 쓰임 |
|---|---|
| 변수마다 건너뛸 표(`skipPastOpByVar`) | 그 변수가 바뀌면 이 표대로 건너뛴다 |
| 연산마다 캐시 번호(`cacheIndex`), 연산 수 | 인스턴스의 캐시 배열을 연산 수만큼만 잡는다 |
| 변수마다 읽는 위치, 위치마다 변수 번호 | 처음 셀 때 어느 칸을 어느 변수가 읽었는지 모은다. 별칭(3절)이면 위치를 합쳐 표를 새로 만든다 |
| 같은 위치에서 시작하는 부분식 사슬(`sameStartOpChain`) | 위의 표를 만들 때만 쓴다 |

**인스턴스마다**

| 무엇 | 크기 |
|---|---|
| 연산마다 지난번 값(캐시 배열) | 연산 수 |
| 구독 함수 하나 | 식이 읽는 칸이 몇 개든 하나. 칸 여럿에 같은 함수를 걸고, 불릴 때 받은 leafIndex로 그 칸의 표를 고른다 |
| 읽은 칸마다 쓸 표 | 칸 수. 대개 정의의 표를 가리키기만 한다 |
| 지난번 결과 | 값 하나. 다시 센 값이 같으면 DOM에 쓰지 않는다 |

인스턴스 몫을 작게 두는 것이 중요하다 - 5절.

## 3. 변수

store 칸을 읽는 명령을 "같은 칸을 읽는가"로 묶은 것이 변수다. 건너뛸 표는 변수마다 하나다.

- 같은 슬롯을 여러 번 읽으면 한 변수다. `a + a`에서 a가 바뀌면 두 위치가 함께 바뀐다 - 한
  위치만 바뀌는 경우는 없다.
- 같은 슬롯이라도 값 칸과 길이 칸은 다른 변수다. `LOAD_VAR a`와 `LOAD_STRING_LENGTH a`는 a의 값
  칸을 읽어 같은 변수이고, `LOAD_ARRAY_LENGTH a`는 길이 칸을 읽어 다른 변수다.
- `READ_LEAF`(인덱스 접근 `a[i].b`에서 요소 칸을 읽는 명령)는 하나하나가 따로 변수다. 어느 칸을
  읽는지는 i에 따라 실행 중에 정해지지만, 읽는 명령의 위치는 바이트에 고정돼 있다. 요소 칸이
  바뀌면 그 칸의 leafIndex를 내는 앞부분(`a[i].b`의 `a`, `i`, `ELEM_AT`, `FIELD_AT`)은 건너뛰고
  `READ_LEAF`만 다시 읽는다.

**별칭** - 부모가 같은 칸을 두 prop으로 넘기면(자식의 `${x + y}`에서 x, y가 같은 칸) 식 정의로는
다른 변수가 한 칸을 가리킨다. 그 칸이 바뀌면 두 변수가 함께 바뀌므로, 인스턴스를 만들 때 두
변수의 위치를 합쳐 정렬하고 그 인스턴스용 표를 만든다. 흔하지 않아 인스턴스마다 만들어도 된다.

## 4. 비율 판단이 없어진 이유

앞선 설계(v4, 6절)는 다시 셀 때마다 사슬을 따라 "이 부분식이 바뀐 위치를 품는가"를 비교했다.
건너뛸 것이 적으면 이 비교 비용이 이득보다 커, "다시 계산할 연산 비율이 0.75를 넘으면 처음부터
센다"는 판단을 따로 두었다.

미리 계산한 표에서는 다시 셀 때 비교가 없다. 명령마다 표를 한 번 조회할 뿐이라 판단이 필요 없다.
node에서 잰 최악(건너뛸 것이 없는 경우)도 처음부터 세는 것보다 약간 느린 정도였고, 그 차이가
커지는 것은 식이 255바이트 한도에 가깝게 클 때뿐인데 그런 식은 실제 템플릿에 없다. 브라우저에서
건너뛸 것이 없는 경우만 따로 재지는 않았다.

## 5. 측정 - 브라우저

주문 목록 1만 행, 행마다 식 셋(금액, 재고, 경고). 대상마다 페이지를 따로 띄우고 실제 버튼을
`.click()`으로 눌러, 클릭부터 DOM 반영까지를 30회 중앙값으로 쟀다(ms, 헤드리스 Chrome, brotli).

```
금액  (row.price * row.qty - row.discount) * (100 + tax) / 100 * rate
재고  row.stock - row.qty
경고  row.qty > 0 && row.stock - row.qty < 5 && row.price * row.qty > threshold
```

| 버튼 | quble 부분 재평가 | quble 전체 재평가 | Svelte 5 | React + memo | React |
|---|---|---|---|---|---|
| 행 하나 +1 | 0.03 | 0.04 | 0.44 | 2.21 | 11.33 |
| 환율 변경(모든 행 금액이 바뀜) | 6.56 | 6.28 | 10.15 | 22.98 | 17.63 |
| 기준 변경(모든 행 경고를 다시 세지만 값은 거의 그대로) | 1.26 | 3.77 | 1.56 | 16.70 | 12.00 |

**인스턴스 메모리가 명령 수보다 컸다.** 처음 구현은 식이 읽는 칸마다 구독 함수를 따로 만들었다.
1만 행에서 함수가 수만 개 늘어 힙이 21.6MB에서 40MB가 됐고, 기준 변경이 전체 재평가보다
오히려 느렸다(5.17 대 3.77). 건너뛰기를 끄고 끝까지 세도 느렸고, 1000행에서는 차이가 없었다 -
명령 수가 아니라 메모리가 CPU 캐시를 넘친 탓이다. 식 하나에 구독 함수 하나로 줄이자 힙이
27.4MB가 됐고 다시 세기가 전체 재평가보다 빨라졌다. node에서 DOM 없이 재면 이 차이가 안 보인다 -
실제 DOM 작업이 캐시를 밀어낼 때만 드러난다.

**같은 값이면 DOM에 쓰지 않는 것이 가장 컸다.** 기준 변경은 1만 행의 경고 식을 모두 다시 세지만
값은 거의 그대로다. 같은 값도 `setAttribute`로 다시 쓰던 때는 클릭당 약 1.5ms가 거기에 들었다.

**재는 방법이 결과를 바꿨다.**

- 여러 구현을 한 프로세스에서 차례로 재면 V8의 최적화 상태가 서로 섞여 같은 코드가 측정마다
  1.5배까지 흔들렸다. 식과 구현 조합마다 프로세스(브라우저는 페이지)를 따로 띄워 잰다.
- 라운드 최솟값은 GC 비용을 가린다. 중앙값과 p90을 같이 본다.
- 다음 프레임까지 재면 주사율(16.6ms)에 묶여 대상 사이 차이가 안 보인다. DOM 반영 시점은
  MutationObserver로, 레이아웃은 그 자리에서 `offsetHeight`를 읽어 잰다.

## 6. 버린 안

| 안 | 버린 이유 |
|---|---|
| 다시 셀 때마다 사슬을 따라 판정(v4) - 잎 위치에서 가장 바깥 부분식부터 "바뀐 위치를 품는가"를 보며 안쪽으로 들어간다. 다시 계산할 연산 비율이 0.75를 넘으면 처음부터 센다 | 판정 비용 때문에 비율 판단이 따로 필요했다. 변수마다 표를 미리 계산하면 비교가 없어지고 판단도 필요 없다(4절). 표 메모리는 식 정의당 한 번이라 인스턴스 수와 무관하다 |
| 식이 읽는 칸마다 구독 함수를 따로 둔다 | 칸마다 건너뛸 표가 달라 자연스러운 모양이지만, 1만 행에서 힙이 두 배 가까이 늘어 다시 세기가 전체 재평가보다 느려졌다(5절) |
| 건너뛸 표를 인스턴스마다 조밀한 배열(식 길이)로 | 조회는 객체와 같거나 느렸고, 인스턴스마다 배열이 늘어 메모리만 커졌다 |
| 명령어에 건너뛸 자리를 표시 - 컴파일러가 부분식 앞에 `SKIP`(건너뛸 곳, 캐시 칸), 뒤에 `STORE`를 넣고 칸마다 잎 비트마스크를 싣는다 | 런타임 분석은 없어지지만 갱신 속도 이득이 없다. 건너뛸 것이 없을 때 처음부터 평가로 돌아가지 못해 최악 2배 느리다(1682 대 910 ns). 표시할 최소 연산 수를 올려도 풀리지 않는다 |
| 결합/분배 법칙으로 식 모양 바꾸기 - 왼쪽 겹 사슬을 균형 트리로, `x*b0 + x*b1`을 `x*(b0 + b1)`로 | number가 부동소수점이라 묶는 순서를 바꾸면 값이 달라진다(`(0.1 + 0.2) + 0.3` 대 `0.1 + (0.2 + 0.3)`). 잎 5~6개 식에서는 앞쪽 잎은 빨라지고 뒤쪽 잎은 느려져 득실이 섞인다 |

**보류** - 식 평가를 wasm으로. wasm 해석기는 JS 해석기보다 약 2배 빨랐고, opcode를 wasm 함수로
컴파일하면 실제 크기 식이 약 10ns였다(대부분 호출 비용). 5절에서 보듯 지금 병목은 식 계산이 아니라
메모리와 DOM 쓰기라 넣지 않았다.

## 7. 남은 것

- **인덱스 접근과 배열 구조 변경** - 캐시해 둔 `ELEM_AT` 결과(요소의 leafIndex)는 인덱스가 그대로여도
  배열 요소가 빠지거나 순서가 바뀌면 낡는다. expr-tree-rebind.draft.md의 재배선과 함께 설계한다.
- **여러 칸이 한 번에 바뀌는 경우** - 핸들러 하나가 칸 여럿을 바꾸면 칸마다 한 번씩 다시 센다. 값은
  맞다(칸마다 그 칸의 길을 다시 세므로 마지막에는 바뀐 칸을 품은 부분식이 모두 새로 계산돼 있다).
  다만 중간 값이 한 번씩 DOM에 쓰인다 - 갱신을 모아 한 번에 처리하는 배치와 함께 본다.
- **환율 변경이 전체 재평가보다 약 5% 느리다**(6.56 대 6.28). 식 계산 자체는 더 빠른데, 프로파일에서
  차이가 텍스트 쓰기와 `reevalExpr` 호출 쪽에서 난다. 원인은 모른다.
- **mount 비용** - quble mount가 React보다 두 배 느리다(1만 행 109 대 58ms). 부분 재평가와 별개로
  본다.
