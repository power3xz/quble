# 식 그래프 - 하위 식을 노드로 나누고 표시와 셈으로 전파하기

진행 중 설계다. 확정되면 BYTECODE.md, EXPR-EVAL.md, SUBSCRIPTION-LAYERS.md, LEAF-STORE-LAYOUT.md로 옮기고 이
문서는 지운다.

## 지금 구조

식 보간(`${count * 2}`), 속성값의 식, `@if`의 식 조건은 식 인스턴스 하나로 센다. 식 인스턴스는 식 하나를 한
스코프에서 세는 단위다. `@for` 안의 식은 행마다 읽는 회차 변수가 달라 행마다 인스턴스가 따로 있고, props만 읽는
식은 행끼리 인스턴스 하나를 공유한다.

식 인스턴스는 자기가 읽는 입력 leaf마다 구독 층(leaf store)에 파생 구독 함수를 건다. 입력 leaf가 바뀌면 구독
층이 그 함수를 호출하고, 함수는 식을 다시 세어 값을 돌려준다. 구독 층은 그 값을 결과 leaf에 기록하고, 값이
바뀌었으면 결과 leaf를 구독하는 DOM 갱신 함수(통지 구독)를 호출한다. 핸들러 하나가 끝날 때 바뀐 leaf를 모아 이
일을 한 번에 하는 것을 flush라고 한다.

`${(a + b) * c}` 하나가 그려지는 길은 이렇다. 괄호 안의 수는 leafIndex다.

```
입력 leaf        a(10)    b(11)    c(12)
                   |        |        |
                   +--------+--------+   같은 파생 구독 함수 하나를 세 leaf에 건다
                            v
식 인스턴스          [(a + b) * c]
                            |            함수가 돌려준 값을 구독 층이 기록한다
                            v
결과 leaf                 (40)
                            |            값이 바뀌었으면 구독 층이 통지 구독을 호출한다
                            v
DOM 갱신 함수        텍스트 노드에 값을 쓴다
```

식 인스턴스는 다른 식 인스턴스의 결과를 읽지 않는다. 식 하나가 읽는 것은 모두 store의 입력 leaf다.

## 왜 바꾸나

삼항 `cond ? a : b`를 넣으려면 두 가지가 필요하다.

- **고른 갈래만 센다.** 이 문서에서 갈래는 삼항의 `a`나 `b`를 가리킨다(`@if`의 가지와 구별한다). 아래 식에서 i가
  배열 길이 이상이 되면 `rows[i]`가 범위 밖 에러를 throw하므로, cond가 거짓일 때 참 갈래를 세면 안 된다.
  ```
  ${i < rows.length ? rows[i].title : ''}
  ```
- **cond를 다른 식과 공유한다.** 아래에서 `@for`가 행 1000개를 그리면 행마다 삼항 식이 하나씩 있다. 1000개의
  삼항과 바깥의 `${a * b > 10}`이 모두 같은 `a * b > 10`을 읽으므로, 이것을 한 번만 세고 싶다.
  ```
  ${a * b > 10}
  @for (row of rows) { ${a * b > 10 ? 'good' : 'bad'} }
  ```

그래서 삼항의 cond와 갈래를 각자 식 인스턴스로 나누고, 삼항 인스턴스가 그 결과를 읽게 한다. 식 인스턴스가 다른
식 인스턴스를 읽게 되므로, 식 인스턴스를 노드로 하는 그래프가 생긴다. IDEAS.md의 `derived`(파생 값이 다른 파생
값을 읽는 구조)도 같은 그래프 위에 올라간다.

## 노드

식 인스턴스 하나가 노드 하나다. 노드 번호는 식 인스턴스 풀의 번호를 그대로 쓴다. 노드 A가 노드 B의 결과를
읽으면 B를 A의 하위 노드, A를 B의 부모라고 한다.

- 하위 식으로 나누는 곳은 삼항(cond와 갈래)과 배열 접근 두 곳뿐이다. 그 밖의 부분식은 나누지 않는다.
  `${a * b > 10}`과 `${a * b + 1}`이 함께 있어도 `a * b`는 각자 센다.
- 나눈 하위 식도 컴파일러의 `intern_expr`를 거쳐 컴포넌트 표현식 테이블에 들어간다. 바이트가 같은 식은 같은 식
  번호가 되므로, 같은 스코프에서는 지금의 공유 맵(`globalExprIndex`, `scopeUid`)이 같은 인스턴스를 찾아 준다.
  위 예에서 1000개의 삼항과 바깥 텍스트가 `a * b > 10` 인스턴스 하나를 함께 쓰는 것이 이 덕분이다.
- 하위 식을 가리키는 명령 `LOAD_EXPR k`의 k는 자기 식 번호보다 작다. 컴파일러가 하위 식을 먼저 테이블에 넣어
  보장한다. 참조를 따라가면 번호가 줄어들기만 하므로 순환이 없다. 컴파일러가 보장하므로 런타임은 검사하지 않는다.

위 예의 그래프는 이렇다. 바깥 텍스트 `${a * b > 10}`은 cond와 바이트도 스코프도 같아, 따로 노드를 두지 않고 cond
노드에 바로 붙는다. 상수 갈래 `'good'`, `'bad'`는 노드를 만들지 않는다.

```
입력 leaf          a       b
                   |       |
                   +---+---+
                       v
노드             [a * b > 10] ------------------------------------> 바깥 텍스트
                       |
         +-------------+-------------+-------- ... --------+
         v             v             v                     v
    [행 0 삼항]    [행 1 삼항]    [행 2 삼항]     ...     [행 999 삼항]
         |             |             |                     |
         v             v             v                     v
    행 0 텍스트    행 1 텍스트    행 2 텍스트             행 999 텍스트
```

## 전파

flush를 두 단계로 나눈다.

1. **표시** - 바뀐 입력 leaf를 읽는 노드에 "다시 세야 함"을 붙이고, 그 노드의 부모, 그 부모의 부모로 표시를
   올린다. 이 단계에서는 아무것도 세지 않는다.
2. **셈** - DOM에 직접 쓰이는 노드부터 센다. DOM에 직접 쓰이는 노드는 텍스트 보간, 속성값, `@if` 조건에 붙은
   노드다. 노드는 세는 도중에 필요한 하위 노드를 요청한다. 표시가 있는 하위 노드는 그때 세고 표시를 지운다. 표시가
   없으면 결과 leaf만 읽는다.

노드 절의 예에서 b가 5이고, 핸들러가 a를 2에서 3으로 바꾼 flush다. `a * b > 10`은 false에서 true가 된다.

```
                       [a * b > 10]     [행 0 삼항]     [행 1 삼항] ... [행 999 삼항]
flush 전                깨끗함            깨끗함          깨끗함           깨끗함
1. 표시 뒤              다시 세야 함      다시 세야 함    다시 세야 함     다시 세야 함
2. 셈 뒤                깨끗함 (true)     깨끗함 ('good') 깨끗함 ('good')  깨끗함 ('good')
```

1. 표시 - a를 읽는 노드는 `a * b > 10` 하나다. 이 노드에 표시하고, 부모인 삼항 1000개에 표시를 올린다.
2. 셈 - DOM에 직접 쓰이는 노드를 차례로 센다.
   - `a * b > 10`은 바깥 텍스트에 붙어 있다. 표시가 있으므로 세어 true를 얻고 표시를 지운다.
   - 행 0 삼항은 cond를 요청한다. cond는 표시가 지워져 있으므로 세지 않고 결과 leaf의 true만 읽는다. 참 갈래
     `'good'`을 고른다.
   - 행 1부터 행 999까지의 삼항도 같다. `a * b > 10`은 이 flush에서 한 번만 셌다.
3. 통지 - 값이 바뀐 결과 leaf 1001개(cond 하나, 삼항 1000개)의 DOM 갱신 함수를 호출한다.

- 순서는 요청이 정한다. 하위 노드는 늘 부모가 요청할 때 세므로, 부모가 셀 때 하위 노드는 이미 이번 flush의 값이다.
  같은 노드를 여러 부모가 요청해도 첫 요청에서 표시가 지워지므로 한 flush에 한 번만 센다.
- 삼항은 cond를 먼저 요청하고, cond 값으로 고른 갈래만 요청한다. 고르지 않은 갈래는 요청하지 않으므로 세지
  않는다. cond가 바뀌어 갈래가 바뀌는 flush에서도 떠나는 갈래는 세지 않는다.
- DOM에 직접 쓰이는 노드인지는 식 인스턴스 풀의 `refCount`로 가린다. `refCount`는 지금도 VM이 텍스트, 속성,
  `@if` 조건에 식을 붙일 때마다 하나씩 올리는 수라, 0보다 크면 DOM에 직접 쓰이는 노드다. 하위 노드로만 쓰이는
  노드는 0이다. 한 노드가 둘 다일 수 있다. `${i < n ? rows[i].x : 0}`과 `${rows[i].x}`가 같은 스코프에 있으면
  `rows[i].x` 노드는 삼항의 갈래이면서 텍스트에 직접 붙는다. 이때 n만 줄어 삼항이 거짓 갈래를 고르면(i는 rows
  범위 안), 텍스트가 그 값을 그리고 있으므로 flush가 `rows[i].x`를 직접 센다.
- `@if (c) { A } @else { B }`도 고르기 노드로 다룬다. 갈래가 값이 아니라 본문 A, B라는 점만 삼항과 다르다. 본문
  안의 노드는 `refCount`가 0보다 커도 flush가 직접 세지 않고, `@if` 노드가 cond를 세어 그 본문을 고른 뒤에 센다.
  그래서 flush가 직접 세는 노드는 "어떤 `@if` 본문에도 들지 않은, DOM에 직접 쓰이는 노드"와 `@if` 노드다. 중첩된
  `@if`는 바깥 `@if`가 안쪽을 요청한다.
  - 지금은 `@if`가 본문을 떼는 일이 통지 구독(`vm.ts`의 `subscribeIfCond`)에 있어, 식을 다 센 뒤에 본문을 뗀다.
    `@if (i < n) { ${rows[i].x} }`에서 i가 n이 되는 flush는 떠나는 본문의 `rows[i].x`를 세다가 `RangeError`를
    throw한다(ISSUES.md). 고르기 노드가 되면 cond를 먼저 세어 본문을 요청하지 않으므로 세지 않는다.
  - 고르기 노드가 정하는 것은 어느 본문인지뿐이다. DOM을 떼고 붙이는 일(detach/attach, lazy build)은 지금처럼
    통지 단계에서 한다.
- DOM 갱신 함수 호출은 셈이 다 끝난 뒤, 값이 바뀐 leaf마다 한 번 한다. 지금과 같다.
- 하위 노드도 부모도 없는 노드는 표시할 것이 자기 하나라 표시 단계를 거치지 않고 바로 센다. 삼항과 배열 접근이
  없는 식은 모두 여기에 해당하므로, 그런 식만 있는 화면(예: 1000행을 한 번에 갱신하는 경우)의 비용은 지금과 같게
  유지한다.

같은 스코프에 `${c ? x : y}`(T1)와 `${x ? c : z}`(T2)가 있으면, 한 식이 다른 식에서는 cond이고 다른 식에서는
갈래다. 여기서 c, x, y, z는 각자 `p > 0`처럼 연산이 든 bool 식이라고 하자. 그러면 넷 모두 노드이고, c와 x는 두
삼항이 공유한다.

```
          [T1: c ? x : y]                    [T2: x ? c : z]
           |cond     |참      |거짓            |cond     |참      |거짓
           |         |        v               |         |        v
           |         |       [y]              |         |       [z]
           |         +-----------> [x] <------+         |
           +-----------------------> [c] <--------------+
```

c와 x의 입력이 함께 바뀌고, c와 x는 둘 다 true인 채인 flush다.

1. 표시 - c, x에 표시하고, 부모인 T1, T2에 표시를 올린다.
2. 셈 - T1이 c를 요청한다. c는 표시가 있으므로 세고 표시를 지운다. c가 true라 T1은 x를 요청한다. x도 세고 표시를
   지운다. 그다음 T2가 x를 요청한다. x는 표시가 지워져 있으므로 결과만 읽는다. x가 true라 T2는 c를 요청하고, c도
   결과만 읽는다.

c와 x는 각자 한 번씩만 센다. 순서를 미리 정하지 않고 먼저 요청한 쪽이 세므로, "x는 c보다 늦게, c는 x보다 늦게"
같은 모순이 생기지 않는다.

### 요청 순서 대신 고르기 먼저 순서를 쓰지 않는 이유

견준 순서는 "표시된 삼항의 갈래를 먼저 모두 정하고, 남은 표시된 노드 중 붙은 노드를 센다"다. 이 순서는 삼항이
다른 삼항의 갈래 안에 있으면 바깥 삼항부터 정해야 한다. `a ? (b ? 'x' : 'y') : 'z'`에서 a가 거짓이 되고, b가
`rows[i].ok`를 읽는데 i가 범위 밖이 되는 flush를 보자. 안쪽부터 정하면 떠나는 갈래 안의 b를 세다가 `RangeError`를
throw한다. 그래서 표시된 부모를 거슬러 올라가 바깥을 먼저 찾아야 한다. 남은 노드를 셀 때도 하위 노드를 먼저 세야
하므로, 결국 요청 순서에 갈래를 미리 정하는 패스를 하나 더한 모양이 된다.

JS로 만든 그래프 프로토타입(노드 계산은 함수, 간선은 Set)에서 flush 한 번의 평균 시간을 쟀다(마이크로초, 3회 실행).

| 장면 | 요청 순서 | 고르기 먼저 |
|---|---|---|
| cond 하나를 1000행 삼항이 공유하고, cond가 뒤집힌다 | 40-45 | 50-59 |
| 1000행 `flag ? row * 2 : 0`에서 flag가 뒤집힌다 | 84-95 | 91-102 |
| 삼항 없는 1000행을 한 batch로 바꾼다 | 41-47 | 42-45 |

고르기 먼저가 빠른 장면은 없다. 게다가 상태가 셋(표시된 삼항 목록, 갈래를 정했는지, 거슬러 오를 때 방문했는지)
더 든다.

## 그래프 자료구조

- 그래프는 표현식 층(expr-layer.ts)이 갖는다. 구독 층은 flush마다 바뀐 입력 leaf 모음을 표현식 층에 한 번
  넘긴다. 표현식 층은 표시와 셈을 끝낸 뒤, 값이 바뀐 결과 leaf 모음을 돌려준다. 구독 층은 바뀐 입력 leaf와 돌려받은
  결과 leaf에 DOM 갱신 함수를 호출한다.
- 노드 상태(깨끗함, 다시 세야 함)는 노드 번호로 인덱싱하는 `Uint8Array` 하나에 둔다.
- 지금은 식 인스턴스마다 파생 구독 함수(클로저)를 하나씩 만들고, 구독 층은 flush마다 이미 호출한 함수와 통지할
  leaf를 Set으로 모은다. 노드 번호로 바꾸면 클로저와 이 Set들이 없어진다.

### 실행 중에 바뀌는 간선

간선은 노드가 읽는 대상(하위 노드나 store leaf)과 노드를 잇는다. 간선이 실행 중에 바뀌는 노드는 두 종류뿐이다.

| 노드 | 바뀌는 것 | 언제 |
|---|---|---|
| 삼항 | 갈래 노드와 잇는 간선이 활성인지 | 갈래가 바뀔 때. 간선 자체는 그 갈래를 처음 고를 때 한 번 붙인다 |
| 삼항 | 잎 갈래 leaf의 구독 | 갈래가 바뀔 때. 고른 잎 갈래만 구독한다 |
| 배열 접근의 값 읽기 | 값 읽기 노드와 store leaf 사이의 간선 | 인덱스가 바뀌어 읽을 요소의 leaf가 달라질 때 |

**삼항의 갈래 간선은 떼지 않는다.** 갈래 노드는 그 갈래를 처음 고를 때 만들어 붙이고, 그 뒤로는 삼항이 반납될
때까지 붙여 둔다. 갈래가 바뀌면 간선이 활성인지만 바꾼다.

- 표시는 활성 간선(cond와 고른 갈래)으로만 부모에게 올라간다. 쉬는 갈래 노드는 입력 leaf의 구독을 유지하므로,
  입력이 바뀌면 자기에게 "다시 세야 함"이 붙지만 삼항까지 올라가지 않는다.
- 쉬는 갈래를 다시 고르면 표시를 본다. 표시가 있으면 그때 세고, 없으면 쉬는 동안 입력이 그대로였으므로 결과
  leaf를 그대로 읽는다.
- 쉬는 노드에 표시가 남아 있으면 다음 표시 단계가 그 노드에서 바로 멈춘다. 그래서 쉬는 갈래의 입력이 계속
  바뀌어도 표시 비용은 첫 번째 한 번뿐이다.
- 쉬는 갈래 안의 값 읽기 노드는 마지막에 읽던 요소의 leaf를 구독한 채 남는다. 그사이 `removeAt`이 그 요소를
  빼고 그 leaf를 다른 요소가 재사용해도 값은 틀리지 않는다. `removeAt`이 배열 필드 leaf에 통지하고, 그 leaf를
  구독한 주소 노드에서 표시가 값 읽기 노드까지 올라가 "다시 세야 함"이 남기 때문이다. 다시 고르면 주소부터 다시
  세어 당겨진 요소를 읽고 구독을 옮긴다. 쉬는 동안 회수된 leaf의 구독 항목 하나가 남는 것이 비용이다.

`${active ? price * qty : count}`에서 active가 true에서 false로 바뀌면 이렇게 된다. 참 갈래는 식이라 노드이고,
cond `active`와 거짓 갈래 `count`는 잎이라 노드 없이 leaf를 바로 읽는다.

```
active가 true일 때                         active가 false가 된 뒤

  active   price   qty    count             active   price   qty    count
    |        |      |                         |        |      |       |
    |        +--+---+     구독하지 않음        |        +--+---+       |
    |           v                             |           v           |
    |      [price * qty]                      |      [price * qty]    |
    |           | 활성                         |           | 비활성    |
    +--> [삼항] <+                             +--> [삼항] <+----------+
```

`price * qty` 노드는 붙은 채 쉰다. price가 바뀌면 이 노드에 표시가 붙지만 삼항은 다시 세지 않는다.

**떼어 내는 방식과 견준 결과.** 갈래가 바뀔 때마다 옛 갈래 노드를 떼고(붙은 곳이 없으면 구독을 풀고 표시를 지운다)
새 갈래 노드를 붙이는(붙을 때 "다시 세야 함"으로 시작한다) 방식과 견주었다. 같은 그래프 프로토타입의 flush 한 번
평균이다(마이크로초, 3회 실행).

| 장면 | 떼어 내기 | 고정 간선 |
|---|---|---|
| 1000행 `flag ? row * 2 : 0`에서 flag가 뒤집힌다 | 88-95 | 37-40 |
| 1000행 `${i < n ? rows[i].x : 0}`에서 n이 바뀌어 절반 행이 떠났다 돌아온다 | 183-187 | 133-157 |
| cond 하나를 1000행 삼항이 공유하고, cond가 뒤집힌다 | 44-45 | 47-48 |
| flag가 false인 채 쉬는 갈래 1000개의 입력만 바뀐다 | 9-10 | 10.5-12 |

- 갈래가 바뀌는 장면은 고정 간선이 빠르다. 붙이고 떼는 비용이 없고, 쉬는 동안 입력이 그대로인 갈래는 다시 세지
  않는다.
- cond를 뒤집는 장면이 조금 느린 것은 표시 단계가 간선마다 활성인지 보기 때문이다. 부모 목록의 항목에 "부모의 몇
  번째 피연산자인지"를 함께 두면 비교 한 번으로 본다.
- 대가는 메모리다. 쉬는 갈래도 식 인스턴스를 든다. 런타임에서 `${n}`과 `${n * 2}`만 다른 `@for` 10000행의 heap
  차이로 잰 식 인스턴스 하나는 약 375 B다(jsdom, 결과 leaf, 부분 재평가 cache, 파생 구독 자리 포함). 처음 고를
  때 만들므로 한 번도 고르지 않은 갈래는 이 비용이 없다.

간선을 붙이고 뗄 때 지킬 규칙은 셋이다. 삼항 갈래는 처음 고를 때만 붙이므로 "붙일 때"만, 값 읽기 노드는 셋 모두
해당한다. "뗄 때"는 노드가 반납될 때(`@for` 행이 지워질 때 등)도 해당한다.

- **순회 중 변경** - 부모 목록을 훑는 도중에, 세던 노드가 간선을 붙이거나 뗄 수 있다. 훑는 쪽이 이를 견뎌야
  한다.
- **붙일 때** - 새로 붙는 노드는 "다시 세야 함"으로 시작하고, 부모에도 표시를 올린다. 떼어져 있던 동안 그 노드의
  입력이 바뀌었을 수 있기 때문이다. 지금은 `everAttached` 필드와 따라잡기 호출(구독을 다시 걸 때 식을 한 번 다시
  세는 것)이 이 일을 하는데, 상태 표시가 대신한다.
- **뗄 때** - 떼는 노드의 표시를 지운다. 표시 단계는 이미 표시된 노드에서 위로 올라가지 않으므로, 표시가 남아
  있으면 나중에 그 노드에 새 부모가 붙었을 때 다음 표시가 새 부모까지 올라가지 않는다.

공유 노드는 부모가 많다. 예를 들어 `@for`가 그리는 1000행이 모두 쓰는 식이면 부모가 1000개다. 부모 목록에서
간선 하나를 찾아 빼면 O(부모 수)라, 1000행을 지우면 O(n^2)이 된다. 간선을 O(1)로 빼려면 간선마다 부모 목록 안의
자기 위치를 기록해 두고, 목록의 맨 끝 간선을 빈자리로 옮길 때 옮겨진 간선의 위치도 고친다. 삼항 갈래를 떼지
않으므로 간선을 빼는 일은 노드를 반납할 때만 생긴다.

## 삼항

삼항은 바이트코드에서 이렇게 나온다.

```
cond  [참 갈래]  [거짓 갈래]  SELECT kinds
```

cond와 두 갈래는 각자 아래 셋 중 한 종류다. `SELECT`는 스택에서 셋을 꺼내 cond 값으로 갈래 하나를 고른다.

| 종류 | 값 | 스택에 올리는 명령 | 예 |
|---|---|---|---|
| 잎 | 0 | `LOAD_LEAF_INDEX`(가칭, 새로 추가) - 슬롯의 leafIndex만 올리고 값은 읽지 않는다 | `active`, `count` |
| 식 | 1 | `LOAD_EXPR k`(새로 추가) - k번 하위 노드를 가리킨다 | `a * b > 10`, `price * qty` |
| 상수 | 2 | `LOAD_CONST`, `LOAD_SMALL_INT`, `LOAD_TRUE`, `LOAD_FALSE` | `'good'`, `0` |

잎 갈래에 leafIndex만 올리는 이유는, 고르기 전에는 그 leaf를 읽지도 구독하지도 않기 위해서다. 고르지 않은 쪽의
leaf를 구독하면, 그 leaf가 바뀔 때마다 결과가 그대로인 삼항을 다시 센다.

`SELECT`의 operand `kinds`(u8)는 세 피연산자의 종류를 담는다.

```
비트   7 6 5   4      3 2     1 0
       0 0 0   cond   참 갈래   거짓 갈래

kinds = (cond << 4) | (참 갈래 << 2) | 거짓 갈래
```

| 식 | cond | 참 갈래 | 거짓 갈래 | kinds |
|---|---|---|---|---|
| `active ? 'on' : 'off'` | 잎 0 | 상수 2 | 상수 2 | `0b0_10_10` = 10 |
| `a * b > 10 ? 'good' : 'bad'` | 식 1 | 상수 2 | 상수 2 | `0b1_10_10` = 26 |
| `active ? count : 0` | 잎 0 | 잎 0 | 상수 2 | `0b0_00_10` = 2 |
| `active ? price * qty : count` | 잎 0 | 식 1 | 잎 0 | `0b0_01_00` = 4 |

- cond는 상수일 수 없어(아래) 잎과 식 두 종류뿐이라 1비트다. cond를 맨 위 비트에 두어, 나중에 cond의 종류가
  늘면 그 위의 빈 비트로 넓힌다. cond를 `kinds >> 4`로 꺼내면 넓혀도 꺼내는 코드가 그대로다.
- 상수와 잎 갈래는 노드를 만들지 않는다. 노드는 식 갈래와 식 cond에만 생긴다.
- 갈래 노드는 그 갈래를 처음 고를 때 만들고 센다. 처음부터 두 갈래를 다 세면, 위의 범위 밖 예에서 고르지 않은
  갈래가 처음 그릴 때 throw한다. `@if`가 비활성 가지를 처음 켤 때 만드는 것(lazy build)과 같다.
- cond가 리터럴만으로 된 식(`true ? a : b`, `1 > 2 ? a : b`)이면 컴파일 에러(`ConstantCondition`)다. `@if`의
  상수 조건이 이미 이 에러이고, 같은 규칙을 따른다.
- 두 갈래의 타입이 같은 원시 타입(number, string, bool)인 경우만 받는다.

## 배열 접근

지금은 `${rows[cursor].title + x}` 하나를 인스턴스 하나가 센다. cursor가 바뀌면 읽는 요소의 leaf가 달라지므로,
인스턴스가 다시 센 뒤 그 leaf로 구독을 옮긴다(EXPR-EVAL.md의 인덱스 접근 구독 다시 걸기). 이것을 노드 셋으로
나눈다.

| 노드 | 하는 일 | 읽는 것 |
|---|---|---|
| 주소 | `rows[cursor].title`이 가리키는 leafIndex를 낸다 | rows, cursor |
| 값 읽기 | 주소 노드가 낸 leafIndex의 값을 낸다 | 주소 노드, 그 leafIndex의 leaf |
| 바깥 식 | `값 읽기 + x`를 센다 | 값 읽기 노드, x |

rows의 요소 0, 1의 title이 leafIndex 40, 43에 있고 cursor가 0일 때다.

```
입력 leaf     rows   cursor        title(40)   title(43)        x
                |      |              |                         |
                +--+---+              |                         |
                   v                  |                         |
노드             [주소] ------------> [값 읽기]                   |
                  40을 낸다            40을 읽는다               |
                                         |                      |
                                         +---> [바깥 식] <------+
```

cursor가 1이 되면 주소 노드가 43을 낸다. 값 읽기 노드는 leaf 40의 구독을 풀고 leaf 43을 구독한다. 주소 노드와 바깥
식의 간선은 그대로다.

- 읽는 leaf가 실행 중에 바뀌는 곳이 값 읽기 노드 하나로 모인다. 바깥 식은 읽는 대상이 고정된다. 그래서 건너뛰기
  표의 `readLeafIndexOpsByVar`, `hasIndexAccess`와 expr-layer.ts의 구독 다시 걸기가 빠진다.
- 같은 스코프의 `${rows[cursor].title}`과 `${rows[cursor].score}`는 `rows[cursor]`까지의 주소 계산을 공유할 수
  있다.
- 노드가 늘어나는 것은 인덱스 접근이 든 식뿐이다. `@for` 안의 식은 대부분 `row.title`처럼 회차 변수의 필드를
  읽고, 이것은 인덱스 접근이 아니다.

## 작업 순서

단계마다 벤치를 main과 비교한다.

1. **숫자 그래프** - 표현식 층의 그래프, 표시와 셈으로 나눈 flush, 상태 배열. 삼항도 배열 접근 분리도 아직 없어
   화면 동작은 지금과 같다.
2. **배열 접근 분리** - 값 읽기 노드와 store leaf 사이의 간선이 실행 중에 바뀌는 첫 사용처다.
3. **삼항과 `@if`** - 고르기 노드가 생기고, 갈래 간선의 활성 여부가 실행 중에 바뀐다. `@if`도 같은 고르기 노드로
   옮겨, 떠나는 본문의 식을 세는 문제(ISSUES.md)를 함께 푼다.

## 정할 것

- 표시를 두 종류로 나눌지. 입력 leaf를 직접 읽는 노드는 "다시 세야 함", 그 위의 부모는 "확인 필요"로 두고, 부모는
  하위 노드를 세어 본 결과가 실제로 바뀐 경우에만 다시 센다. 하위 노드의 값이 그대로면 부모를 세지 않아도 된다.
- DOM에 직접 쓰이지 않는 하위 노드의 결과 leaf를 누가 잡고 누가 반납할지. 지금은 VM이 텍스트나 속성에 식을 붙일
  때 결과 leaf를 잡는다.
- 배열 접근을 나눈 바이트코드의 모양.
- `LOAD_LEAF_INDEX`의 이름.
- `@if`의 쉬는 본문을 삼항 갈래와 같은 규칙으로 둘지. 삼항 갈래는 쉬는 동안 구독을 유지한다. 지금 `@if`는 꺼진
  본문의 식 인스턴스와 DOM을 유지하되 구독을 풀고, 다시 켤 때 따라잡는다. 본문은 DOM까지 들고 있어 구독을
  유지하면 쉬는 동안의 표시 비용이 본문 크기만큼 든다.
- `@for`의 행 본문도 `@for` 노드가 요청하는 구조로 둘지. 개수 `@for`는 `@if`와 같은 문제가 있다.
  `@for (k of n) { ${rows[k].x} }`에서 핸들러 하나가 rows의 마지막 요소를 `removeAt`으로 빼고 n을 줄이면, 떠나는
  행의 `rows[k].x`를 세다가 `RangeError`를 throw한 뒤에 n의 통지 구독이 그 행을 뗀다(ISSUES.md). 배열
  `@for`(`@for (row of rows)`)는 `removeAt`이 통지보다 먼저 그 행을 떼어 이 경로를 타지 않는 것으로 보이나 실행해
  확인하지는 않았다.
