# 구독 층 (draft)

진행 중인 설계 초안이다. main에 머지하기 전에 구현을 읽어 `EXPR-EVAL.md`와
`LEAF-STORE-LAYOUT.md`에 반영하고 이 파일은 지운다.

## 용어

| 낱말 | 뜻 |
|---|---|
| 파생 구독 | 입력으로 값을 만들어 내는 구독. 입력은 leaf 또는 다른 파생 구독이다 |
| 파생 leaf | 파생 구독 트리의 뿌리 값이 놓이는 leaf. 입력 leaf와 달리 vm이 런타임에 잡는다 |
| effect 구독 | leaf 값을 읽어 DOM 같은 바깥을 바꾸는 구독 |
| 입력 leaf | 변수가 놓인 leaf. 파생 구독이 읽는다 |

## 층

```
  DOM 바인딩        텍스트/속성 쓰기, @if/@for 분기 전환
       |  leafIndex를 구독한다 (effect 구독)
       v
  표현식 층         입력을 읽어 식을 세고, 파생 leaf에 set한다
       |  입력 leaf를 구독한다 (파생 구독)
       v
  구독 층           leaf마다 구독 함수 목록, notify, batch
       |
       v
  store             leaf에 값 쓰기/읽기 (set, get), alloc, free
```

DOM 바인딩은 표현식을 모른다. 변수 보간이든 식 보간이든 leafIndex 하나를 구독 층에 구독할
뿐이다. 식 보간은 표현식 층이 식을 만들 때 파생 leaf의 leafIndex를 돌려주고, DOM 바인딩은 그
leafIndex를 변수의 leaf와 똑같이 구독한다. 표현식 층은 구독 층과 store만 쓰고, 구독 층은
표현식을 모르며, store는 구독을 모른다.

```
  DOM 바인딩 -----------------> 구독 층 -> store
                                  ^
  표현식 층 ----------------------+
     (식을 만들면 파생 leaf의 leafIndex를 돌려준다)
```

## 구독 두 종류

| 종류 | 거는 쪽 | 거는 곳 | 불리는 때 | 하는 일 |
|---|---|---|---|---|
| 파생 구독 | 표현식 층 | 입력 leaf | notify 때 먼저 | 식을 다시 세어 파생 leaf에 `set`한다 |
| effect 구독 | DOM 바인딩 | 입력 leaf 또는 파생 leaf | 파생 구독이 모두 끝난 뒤 | leaf의 확정된 값을 DOM에 쓴다 |

effect 구독은 입력 leaf인지 파생 leaf인지 구별하지 않는다. 입력 leaf에는 파생 구독과 effect
구독이 함께 걸릴 수 있고, 같은 leaf 안에서도 파생이 먼저다.

batch를 비울 때 순서는 이렇다.

```
  모아 둔 leaf들
    1. leaf마다 파생 구독을 부른다   -> 파생 leaf에 set (이 단계의 통지는 모아 둔다)
    2. 모아 둔 leaf와 1번에서 새로 모인 leaf마다 effect 구독을 한 번씩 부른다
```

파생 leaf는 다른 파생 구독의 입력이 되지 않으므로 1번은 한 단계로 끝나, 의존 순서 정렬이
필요 없다. 파생 구독을 파생 leaf에 거는 것은 컴파일러가 막는다 - 파생 leaf는 소스에서
이름을 붙일 수 없어 식이 읽는 것은 변수의 leaf뿐이다. 순환도 없다 - 파생 구독이 쓰는 것은
자기 파생 leaf 하나뿐이다.

## 파생 구독의 구조

파생 구독은 트리다. 말단은 입력 leaf를 읽는 곳이고, 안쪽 노드는 파생 구독이며, 뿌리의 값이
파생 leaf에 `set`된다.

- 한 노드의 출력은 부모 하나(또는 파생 leaf)로만 간다. 노드를 공유하지 않는다.
- 하위 결과(`cache[3]`, `cache[7]` 같은 중간 값)는 leaf가 되지 않는다. 노드끼리 함수 호출로
  이어지고, 부분 재평가를 위한 cache 배열로만 남는다.
- leaf를 갖는 것은 effect 구독이 걸리는 뿌리 하나다. DOM 구독이 걸리려면 leafIndex가
  있어야 하기 때문이다.
- 같은 식을 두 번 보간하면 트리와 파생 leaf가 두 벌 생겨 두 번 센다. 지금과 비용이 같다.
- 선례: `IF_EXPR`은 이미 파생 leaf를 잡고 분기가 그것을 구독한다(`vm.ts`의 `bindExpr` 주석).
  분기가 구독하는 것은 effect 구독이고, 보간 식으로 넓히는 셈이다.

### 노드 공유 (이번 범위에서 제외)

`{ (a + b) * c }`와 `{ (a + b) - d }`가 `a + b`를 한 번만 세어 나눠 쓰면 노드의 부모가 둘이 되어
그래프가 된다. 풀려면 파생 구독이 파생 구독을 직접 구독하는 구조가 필요하고, 그때는 노드가
부모 목록과 깊이를 들고 해제 때 부모 수도 세야 한다. 같은 식 전체를 공유하는 것(뿌리 공유)은
부모가 늘지 않아 effect 구독자 수만 세면 된다. 둘 다 컴파일러가 같은 식에 같은 번호를 주는지
확인이 필요하다. 얻는 것이 중복 계산 절감뿐이고 비용은 모든 노드에 든다.

## 지금과 달라지는 것

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 식 결과 | 구독 함수가 `lastValue`와 비교해 `onValue`로 DOM에 바로 쓴다 | 파생 leaf에 `set`한다. 같은 값 건너뛰기는 `set`이 한다 |
| 같은 flush에서 읽는 leaf 여럿이 바뀜 | 구독 함수가 `flushLeaves`와 `handledFlush`로 한 번만 세도록 막는다 | 막는 장치는 표현식 층에 그대로 남는다. 달라지는 것은 파생 구독이 모두 끝난 뒤 DOM을 쓰므로 중간 값이 DOM에 닿지 않는 점 |
| DOM 쓰기 | 식 구독 함수 안 | effect 구독 |
| `bindExpr` | 식을 세고 `update` 콜백을 식 구독 함수에 넘긴다 | 표현식 층에 식을 만들어 파생 leaf의 leafIndex를 받고, 그 leaf를 `bindVar`처럼 구독한다. `update`는 표현식 층에 들어가지 않는다 |

바뀌지 않는 것: cache와 건너뛰기 표를 쓰는 부분 재평가, 인덱스 접근의 구독 다시 걸기.

## 비용

- 보간 식마다 leaf가 하나 는다.
- DOM에 쓰는 함수가 불리는 횟수는 지금과 같다. 지금은 식 구독 함수가 `onValue`를 직접 부르고,
  바뀐 뒤에는 `fire`가 그 함수를 부른다. 늘어나는 것은 그 사이의 `set`, `notify`, `fire` 경로다.
- 이 비용이 `bench-expr`의 `orders`, `orders-toggle`에서 얼마인지 구현 뒤에 잰다. 크면 파생
  leaf 없이 effect 구독을 파생 구독 뿌리에 바로 거는 쪽을 검토한다.

## 정한 것

- 파생 leaf는 다른 식의 입력이 되지 않는다.
- `@if` 조건은 식의 파생 leaf를 effect 구독으로 구독한다.
- 가지는 파생 leaf를 구독하는 effect 구독만 관리한다. 가지를 다시 붙일 때 따라잡기는 파생 leaf
  값을 읽어 DOM에 쓰는 일뿐이다.
- 파생 구독은 파생 leaf의 effect 구독자가 없어질 때 입력 leaf에서 모두 해제한다. 그래서 숨은
  가지는 식을 세지 않는다. 구독자가 0에서 1이 되면 다시 걸고 식을 세어 파생 leaf를 맞춘다.
  이를 위해 파생 leaf의 effect 구독자 수를 알아야 한다.

## 정할 것

- 다시 걸 때 cache. 숨은 동안 입력이 바뀌었을 수 있어 cache는 옛 값이다. 처음부터 다시
  세야 하는지, 지금 `restoreBranchSubs`가 이를 어떻게 피하는지 코드를 읽어 확인한다.
- effect 구독자 수가 0이나 1을 넘는 경우. 보간마다 파생 leaf를 따로 잡으면 구독자는 항상
  하나라 개수 관리가 필요 없다. 뿌리를 공유하면 필요하다.
- effect 구독 안에서 입력 leaf에 `set`하는 코드가 있는지(`vm.ts`의 `store.set` 호출들이 flush
  밖 핸들러 경로뿐인지) 확인한다.
