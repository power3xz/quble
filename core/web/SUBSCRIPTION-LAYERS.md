# 구독 층 (draft)

진행 중인 설계 초안이다. main에 머지하기 전에 구현을 읽어 `EXPR-EVAL.md`와
`LEAF-STORE-LAYOUT.md`에 반영하고 이 파일은 지운다.

## 층

```
  DOM 바인딩        텍스트/속성 쓰기, @if/@for 분기 전환
       |  어떤 칸이든 leafIndex를 구독한다 (통지 후 구독)
       v
  표현식 층         입력 칸을 읽어 식을 세고, 결과 칸에 set한다
       |  입력 칸을 구독한다 (연계 구독)
       v
  구독 층           칸마다 구독 함수 목록, notify, batch
       |
       v
  store             칸에 값 쓰기/읽기 (set, get), alloc, free
```

위 그림은 값이 흐르는 순서다. 호출 관계는 아래에 따로 그린다.

DOM 바인딩은 표현식을 모른다. 변수 보간이든 식 보간이든 leafIndex 하나를 구독 층에 구독할
뿐이다. 식 보간은 표현식 층이 식을 만들 때 결과 칸의 leafIndex를 돌려주고, DOM 바인딩은 그
leafIndex를 변수의 칸과 똑같이 구독한다. 표현식 층은 구독 층과 store만 쓰고, 구독 층은
표현식을 모르며, store는 구독을 모른다.

```
  DOM 바인딩 -----------------> 구독 층 -> store
                                  ^
  표현식 층 ----------------------+
     (식을 만들면 결과 칸의 leafIndex를 돌려준다)
```

## 구독 두 종류

| 종류 | 거는 쪽 | 불리는 때 | 하는 일 |
|---|---|---|---|
| 연계 구독 | 표현식 층 | notify 때 먼저 | 식을 다시 세어 결과 칸에 `set`한다 |
| 통지 후 구독 | DOM 바인딩 | 연계 구독이 모두 끝난 뒤 | 칸의 확정된 값을 DOM에 쓴다 |

통지 후 구독이 거는 칸은 변수의 칸이든 식의 결과 칸이든 구별하지 않는다. 변수의 칸에는 연계
구독과 통지 후 구독이 함께 걸릴 수 있고, 같은 칸 안에서도 연계가 먼저다.

batch를 비울 때 순서는 이렇다.

```
  모아 둔 칸들
    1. 칸마다 연계 구독을 부른다     -> 결과 칸에 set (값이 바뀐 칸만 통지 후 목록에 든다)
    2. 칸마다 통지 후 구독을 한 번씩 부른다
```

결과 칸을 다른 식이 입력으로 읽지 않으면 연계는 한 단계로 끝나, 1번에 의존 순서 정렬이
필요 없다.

## 칸이 되는 조건

- 칸을 갖는 것은 보간이나 속성에 묶이는 식의 최종 결과 하나다. DOM 구독이 걸리려면
  leafIndex가 있어야 하기 때문이다.
- 하위 결과(`cache[3]`, `cache[7]` 같은 중간 값)는 칸이 되지 않는다. 식 안에서 함수 호출로
  이어지고, 부분 재평가를 위한 cache 배열로만 남는다.
- 선례: `IF_EXPR`은 이미 파생 칸을 잡는다(`vm.ts`의 `bindExpr` 주석). 보간 식으로 넓히는 셈이다.

## 지금과 달라지는 것

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 식 결과 | 구독 함수가 `lastValue`와 비교해 `onValue`로 DOM에 바로 쓴다 | 결과 칸에 `set`한다. 같은 값 건너뛰기는 `set`이 한다 |
| 같은 flush에서 읽는 칸 여럿이 바뀜 | 구독 함수가 `flushLeaves`와 `handledFlush`로 한 번만 세도록 막는다 | 막는 장치는 표현식 층에 그대로 남는다. 달라지는 것은 연계 구독이 모두 끝난 뒤 DOM을 쓰므로 중간 값이 DOM에 닿지 않는 점 |
| DOM 쓰기 | 식 구독 함수 안 | 통지 후 구독 |
| `bindExpr` | 식을 세고 `update` 콜백을 식 구독 함수에 넘긴다 | 표현식 층에 식을 만들어 결과 칸의 leafIndex를 받고, 그 칸을 `bindVar`처럼 구독한다. `update`는 표현식 층에 들어가지 않는다 |

바뀌지 않는 것: cache와 건너뛰기 표를 쓰는 부분 재평가, 인덱스 접근의 구독 다시 걸기.

## 비용

- 보간 식마다 칸이 하나 는다.
- DOM에 쓰는 함수가 불리는 횟수는 지금과 같다. 지금은 식 구독 함수가 `onValue`를 직접 부르고,
  바뀐 뒤에는 `fire`가 그 함수를 부른다. 늘어나는 것은 그 사이의 `set`, `notify`, `fire` 경로다.
- 이 비용이 `bench-expr`의 `orders`, `orders-toggle`에서 얼마인지 구현 뒤에 잰다.

## 정할 것

## 정한 것

- 결과 칸은 다른 식의 입력이 되지 않는다. 연계는 한 단계라 의존 순서가 필요 없다.
- `@if` 조건은 식의 결과 칸을 통지 후 구독으로 구독한다.
- 가지는 결과 칸 구독(통지 후 구독)만 관리한다. 가지를 다시 붙일 때 따라잡기는 결과 칸 값을
  읽어 DOM에 쓰는 일뿐이다.
- 연계 구독은 결과 칸의 통지 후 구독자가 없어질 때 입력 칸에서 모두 해제한다. 그래서 숨은
  가지는 식을 세지 않는다. 구독자가 0에서 1이 되면 다시 걸고 식을 세어 결과 칸을 맞춘다.
  이를 위해 결과 칸의 통지 후 구독자 수를 알아야 한다.

## 정할 것

- 다시 걸 때 cache. 숨은 동안 입력이 바뀌었을 수 있어 cache는 옛 값이다. 처음부터 다시
  세야 하는지, 지금 `restoreBranchSubs`가 이를 어떻게 피하는지 코드를 읽어 확인한다.
- 구독자 수가 0이나 1을 넘는 경우. 보간마다 결과 칸을 따로 잡으면 구독자는 항상 하나라 개수
  관리가 필요 없다. 같은 식의 결과 칸을 공유하면 필요하다.
